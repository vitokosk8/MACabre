# P2 Specifications

Expansion techniques (priority P2) from the [attack catalog](../attack-catalog.md). The theory behind each attack is in [docs/attacks](../attacks/README.md). Each technique is specified and implemented one at a time, using the same fields as the [P1 specifications](P1.md).

Status legend: ✅ lab-validated, ⏳ planned.

## Static MAC Impersonation ✅

**Family**: MAC Address & CAM Table. **Priority**: P2.

- **Protocol**: IEEE 802.1D static filtering entries. A statically registered address is bound to one port and is not relearned from traffic.
- **Technical reference**: IEEE 802.1D (static filtering entries) and IEEE 802.1Q. Vendor documentation on static MAC bindings and port security.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to a port other than the registered one, and an authorized test network. The registered MAC must be known.
- **Compatibility**: switches with static MAC entries. The outcome depends on the implementation, so each switch is tested separately.
- **Expected behavior**:
  - Vulnerable: frames that claim the registered MAC from another port move the binding, or the switch forwards them and delivers traffic for that MAC to the attacker.
  - Protected: the binding stays on the registered port, frames from another port are dropped or logged, and traffic for the registered MAC still reaches the victim.
- **Evidence**:
  - On a lab bridge, the static entry before and after the impersonating frames, and the frames the monitor receives.
  - Unicast traffic for the registered MAC, sent after the impersonation, and which port receives it.
- **Impact**: traffic for a registered device, such as a gateway or a server, reaches the attacker.
- **Mitigations**: port security on bound ports, with violation shutdown. Alerts on frames that conflict with a static entry. A reviewed inventory of static bindings.
- **Execution risk**: **Active Test** on an authorized port. Impersonating a registered device on a production network is **Destructive Lab** only.

### Implementation notes

- The module sends broadcast frames with a registered source MAC, an experimental EtherType (0x88B5) and a fixed payload. No host parses them as IP or ARP.
- Frames are sent in batches at a configured rate, up to 100 frames per second. A dry run builds the frames and sends nothing.
- The attack does not change the attacker's interface MAC, so the source address is set only in the frames.

### Lab validation

`scripts/lab/static_mac_impersonation_lab.sh` builds a bridge with a victim port holding a static entry for the victim's MAC, an attacker port and a monitor port. Four phases:

1. Baseline: no frames are sent.
2. Control: the attacker sends frames with its own MAC. The monitor receives them, and the attacker's MAC is learned on the attacker's port.
3. Impersonation: the attacker sends frames with the registered MAC. The monitor receives them all, and the static entry moves to the attacker's port.
4. Redirect: the monitor sends unicast frames to the registered MAC. The attacker receives all of them, and the victim receives none.

Result on the Linux bridge: the binding moves, although the entry keeps its static flag. This validates the attack against this bridge only. Whether managed switches keep the binding, and whether their port security drops the frames, is not tested here and needs a real switch.

## Port Security Exhaustion 🔨

**Family**: MAC Address & CAM Table. **Priority**: P2.

- **Protocol**: IEEE 802.1D MAC learning, with a vendor port security limit on the number of learned MAC addresses per port.
- **Technical reference**: IEEE 802.1D (learning). Vendor documentation on port security (maximum MAC count and violation modes).
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the port under test, and an authorized test network.
- **Compatibility**: switch ports with a MAC address limit. Each vendor defines the violation action differently.
- **Expected behavior**:
  - Vulnerable: the port reaches its MAC limit and the legitimate host loses connectivity, or the port is shut down, without any malicious traffic from that host.
  - Protected: the violation restricts only the offending addresses, the legitimate host keeps access, and the event is logged.
- **Evidence**:
  - On a lab bridge, the number of addresses the attacker's port learns from the frames sent.
  - The legitimate host's entry on its own port, after the flood.
  - On a real switch with a limit configured, the port state and the host's connectivity after the limit is reached. Not yet tested.
- **Impact**: the legitimate host on the port is blocked, and the port may be shut down until an operator clears it.
- **Mitigations**: a sensible limit per port, sticky learning, a violation action that restricts traffic instead of shutting the port when availability matters, and monitoring of violation counters.
- **Execution risk**: **Active Test** on an authorized port. Exhausting a production port's limit is **Destructive Lab** only.

### Implementation notes

- The module sends broadcast frames, each with a new random locally administered unicast source MAC, an experimental EtherType (0x88B5) and a fixed payload.
- Frames are sent in batches at a configured rate, up to 100 frames per second. A dry run builds the frames and sends nothing.

### Lab validation

`scripts/lab/port_security_exhaustion_lab.sh` builds a Linux bridge with an attacker port and a victim port. Phase 0 learns the victim's MAC on its port. Phase 1 sends frames with new source MACs from the attacker's port and counts the addresses learned there. Result: one learned address per frame, and the victim's entry kept on its port.

Run on an OrbStack Ubuntu VM: the baseline learns 1 address on the attacker's port (its own, from its IPv6 traffic), and the flood adds 20 for 20 frames. The victim's entry stays on its own port. The lab passes.

A Linux bridge has no per-port MAC limit, so the lab cannot produce the violation. The status is 🔨 Implemented until a real switch with a configured limit is tested.

## MAC Move / Mobility Abuse ✅

**Family**: MAC Address & CAM Table. **Priority**: P2.

- **Protocol**: IEEE 802.1D MAC learning. A dynamic entry follows the latest frame from a source address. Vendor mobility and move-detection features add thresholds on top of this.
- **Technical reference**: IEEE 802.1D (learning). Vendor documentation on MAC move detection and mobility (for example, moves per minute and allowed ports).
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to a port other than the host's, and an authorized test network. The target MAC must be known.
- **Compatibility**: switches that learn dynamic entries. Move detection and its thresholds are vendor-specific.
- **Expected behavior**:
  - Vulnerable: one frame that claims the host's MAC from another port moves the entry, and traffic for the host is delivered to the attacker.
  - Protected: moves outside the allowed set are rejected, moves over the threshold are blocked or logged, and traffic for the host still reaches it.
- **Evidence**:
  - On a lab bridge, the entry for the host's MAC before and after the move frame.
  - The traffic for the host's MAC delivered to the host and to the attacker, before and after.
  - On a real switch, the move-detection result and its log entry. Not yet tested.
- **Impact**: traffic for a learned host is delivered to the attacker until the host sends again.
- **Mitigations**: move detection with thresholds and alerts, port restrictions for addresses that must not move, and 802.1X or static entries for sensitive hosts.
- **Execution risk**: **Active Test** on an authorized port. Moving a production host's entry is **Destructive Lab** only.

### Implementation notes

- The module sends one or a few broadcast frames, each with the target MAC as source, an experimental EtherType (0x88B5) and a fixed payload. It sends them once and does not keep the entry moved.
- Up to 100 frames per run. A dry run builds the frames and sends nothing.

### Lab validation

`scripts/lab/mac_move_lab.sh` builds a Linux bridge with a victim, an attacker and a monitor port. The victim's entry is dynamic. One move frame from the attacker's port moves the entry to the attacker's port, and all unicast traffic for the victim's MAC then reaches the attacker. The lab validates the move on this bridge. Move thresholds, move logging and allowed-port policies are not tested, because a Linux bridge has none of them.

## Unknown Unicast Flooding ✅

**Family**: MAC Address & CAM Table. **Priority**: P2.

- **Protocol**: IEEE 802.1D forwarding. A frame whose unicast destination is not in the table is flooded to every port in the VLAN.
- **Technical reference**: IEEE 802.1D (forwarding and learning rules). Vendor documentation on unknown unicast rate limiting and storm control.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to a port in the VLAN, and an authorized test network. Nothing needs to be sent.
- **Compatibility**: switches that flood unknown unicast frames in a VLAN. Many have storm control or rate limits for this traffic.
- **Expected behavior**:
  - Vulnerable: unicast frames for unknown or aged-out destinations reach a host on any port, and the host can capture them.
  - Protected: unknown unicast is rate limited, or the table ages and relearns quickly enough that few destinations are unknown.
- **Evidence**:
  - On a lab bridge, the number of unicast frames to other hosts that a listener on another port captures, and the destinations they go to.
  - That the unknown destination is not learned, and that the flood does not fill the table.
  - On a real switch, the flood rate for unknown unicast traffic, and any storm control or rate limit. Not yet tested.
- **Impact**: traffic to hosts whose entries have aged out, or that were never learned, is visible to any host on the VLAN.
- **Mitigations**: storm control or rate limits for unknown unicast, adequate table size and aging times, encryption at the application layer for sensitive traffic.
- **Execution risk**: **Passive** on an authorized port. The module sends nothing. Capturing other hosts' traffic on a production network is **Destructive Lab** only.

### Implementation notes

- The module captures frames on the chosen interface for the listening time, and counts unicast frames whose source and destination are not this host, excluding broadcast and multicast.
- It sends nothing and learns no addresses on the switch.

### Lab validation

`scripts/lab/unknown_unicast_flooding_lab.sh` builds a Linux bridge with a victim, a monitor and an idle attacker port. The victim sends unicast frames to a destination the switch has never learned. The listener on the monitor port captures all of them, and the unknown destination is not learned. The lab validates flooding on this bridge. Rate limiting, storm control and table aging are not tested.

## ARP Table Exhaustion 🧪

**Family**: ARP. **Priority**: P2.

- **Protocol**: ARP (RFC 826) and the neighbor (ARP) table of the device, which has a size limit and an eviction policy.
- **Technical reference**: RFC 826 (ARP). Operating system documentation for neighbor table limits (on Linux, the `gc_thresh` settings).
- **Requirements**: root or `CAP_NET_RAW` on an interface on the victim's segment, and an authorized test network. The victim's address must be known.
- **Compatibility**: any host or router with a neighbor table limit. Limits and eviction differ by system.
- **Expected behavior**:
  - Vulnerable: requests from many new senders fill the table, and a legitimate entry, such as the gateway, is evicted, so traffic to it fails until it is learned again.
  - Protected: the table is sized for the segment, limits apply per port, and legitimate entries survive a burst of new ones.
- **Evidence**:
  - On the victim, the number of entries before and after the requests.
  - Whether the gateway's entry survives, once the table has reached its limit.
  - On the target device, the same measurements. Not yet tested.
- **Impact**: the victim cannot reach hosts whose entries were evicted, until they are learned again.
- **Mitigations**: table sizes sized for the segment, limits on entries created per port, Dynamic ARP Inspection and DHCP snooping so that only trusted bindings create entries.
- **Execution risk**: **Active Test** on an authorized segment. Filling a production device's table is **Destructive Lab** only.

### Implementation notes

- The module sends broadcast ARP requests whose target is the victim's address and whose sender is a new random address and MAC in the chosen subnet.
- Requests are sent in batches at a configured rate, up to 100 per second. A dry run builds the requests and sends nothing.

### Lab validation

`scripts/lab/arp_table_exhaustion_lab.sh` runs the victim, a gateway and the attacker on a bridge, on an OrbStack Ubuntu VM. The victim pings the gateway, and it pings the gateway every 10 s during sampling so that entry stays in use. The lab samples the victim's table every second for 60 s, first without a flood (control) and then after a burst of 1100 requests from fake senders at 100/s. Result: PASS.

- Control: the table holds 1 entry, and the gateway's entry is present.
- Flood: the table peaks at about 600 entries and holds about 511 for roughly 30 s before expiring to about 395. The gateway's entry survives.

The kernel's limit (gc_thresh3) is not exposed in this VM, so the lab reports observed values. The level near 511 is close to the default soft threshold gc_thresh2 (512); that is a hypothesis, not a measured value. Other systems use other limits and eviction rules: test the target device.

## Proxy ARP Abuse ✅

**Family**: ARP. **Priority**: P2.

- **Protocol**: ARP (RFC 826). A router with proxy ARP answers requests for addresses on networks it routes to, with its own MAC address.
- **Technical reference**: RFC 826 (ARP). Router documentation for proxy ARP (on Linux, the `proxy_arp` setting per interface).
- **Requirements**: root or `CAP_NET_RAW` on an interface of the segment under test, and an authorized test network. The sender address on that segment must be known.
- **Compatibility**: routers with proxy ARP enabled on an interface. Many vendors disable it by default.
- **Expected behavior**:
  - Vulnerable: a router answers for addresses outside the segment with its own MAC, so hosts send traffic for those addresses to the router.
  - Protected: proxy ARP is off where routing is used, or limited to the segments that need it, and no answer comes for other networks.
- **Evidence**:
  - On a lab router, the MAC that answers for an address on the other segment, with proxy ARP off and on.
  - On the target router, the same probe from each access port. Not yet tested.
- **Impact**: traffic from the segment for addresses on other networks reaches the router, which can bypass segmentation.
- **Mitigations**: disable proxy ARP where routing is used, restrict it to the segments that need it, and use private VLANs or port isolation to block host-to-host traffic.
- **Execution risk**: **Active Test** on an authorized segment. Probing a production router is **Destructive Lab** only if its answers are used to send traffic.

### Implementation notes

- The module sends one broadcast ARP request per target from the sender address, and reads the replies for the wait time. It refuses targets inside the sender's segment.
- It changes nothing on the network. The lab changes proxy ARP on the router, not the probe.

### Lab validation

`scripts/lab/proxy_arp_abuse_lab.sh` runs an attacker on one segment, a host on another, and a Linux router between them. With proxy ARP off on the router's segment-facing interface, nothing answers for the host. With it on, the router answers with its own MAC. The lab validates the router's behavior on this setup. Other vendors' defaults are not tested.

## QinQ / VLAN Stacking Abuse 🧪

- Protocol: IEEE 802.1ad (provider bridging) outer tag, TPID 0x88A8, around an 802.1Q customer tag (TPID 0x8100).
- Technical reference: IEEE 802.1ad; Linux bridge `vlan_protocol 802.1ad`.
- Requirements: a customer port that can send frames; a provider edge that accepts the outer tag from that port.
- Compatibility: frames are built with Scapy and sent from one interface; no vendor-specific behavior is assumed.
- Expected behavior: a provider edge that trusts the customer's outer tag forwards the frame on the chosen service VLAN; one that sets or checks the outer tag itself drops or rewrites it.
- Evidence: frames sent once; the lab observes the provider side only.
- Impact: the customer chooses the service a frame uses, which can leak traffic into another customer's service.
- Mitigations: set the outer tag on ingress; drop frames whose outer tag is not provisioned for the port; separate service ranges.
- Execution risk: low; the attack sends a fixed, small number of frames.
- Implementation notes: frames are sent once (not repeated), dry run builds frames without sending. Distinct from Double-Tagging, which uses two 802.1Q tags.
- Lab validation: `scripts/lab/qinq_stacking_lab.sh`, on an OrbStack Ubuntu VM, with an edge bridge that has VLAN filtering and an 802.1ad outer tag. Result: PASS.
  - Baseline: the customer port is a member only of customer VLAN 20, and the provider side receives no stacked frame.
  - Attack: the customer port is also a member of service VLAN 100. The provider side receives 3 stacked frames, with outer VLAN 100 and inner VLAN 20 intact.
  - Scope: the lab shows how the edge forwards a customer-chosen outer tag. Provider edges that set the outer tag themselves need the target device.

## DHCP Release Spoofing 🧪

- Protocol: DHCPv4 (RFC 2131), DHCPRELEASE.
- Technical reference: RFC 2131, section 4.4.4 (DHCPRELEASE); the server identifies the lease by client identifier or MAC and by address.
- Requirements: the victim's MAC and leased address (both copied from its traffic); the server's address.
- Compatibility: any DHCPv4 server that accepts releases without authentication; the lab uses dnsmasq.
- Expected behavior: the server frees the victim's lease when the release carries the victim's MAC; a release with another MAC is ignored.
- Evidence: the lab reads the server's lease file before and after each release.
- Impact: the address is free to another host while the victim still uses it, which causes a conflict.
- Mitigations: DHCP snooping that checks the port and MAC against the lease; conflict monitoring; duplicate address detection on clients.
- Execution risk: low; one release per message, no traffic flood.
- Implementation notes: releases are sent once each, with a fresh transaction ID; dry run builds the messages without sending. The release is broadcast when no server MAC is given.
- Lab validation: `scripts/lab/dhcp_release_spoofing_lab.sh` validates the control and the attack on dnsmasq. Not yet tested on a MikroTik or another server. Result on an OrbStack Ubuntu VM with dnsmasq 2.91: PASS (the lease survived a release with another MAC; a release with the victim's MAC freed the address from the server's file).

## DHCP Option Manipulation 🔨

- Protocol: DHCPv4 options (RFC 2132): domain (15), NTP server (42), search domains (119), classless static routes (121, RFC 3442), WPAD (252).
- Technical reference: RFC 2132, RFC 3442, RFC 3397 (search domains encoding).
- Requirements: the legitimate server's address and MAC (copied), the same as DHCP Spoofing.
- Compatibility: any DHCPv4 client that accepts options from the first valid server. The lab uses dnsmasq and a scapy client.
- Expected behavior: the client receives the chosen options in the acknowledgment; whether it applies them depends on the client.
- Evidence: the lab records the WPAD option the client receives, with the legitimate server running and stopped.
- Impact: a changed gateway, route, search list or proxy configuration sends the client's traffic or name resolution through the attacker.
- Mitigations: DHCP snooping with trusted server ports; monitoring of option changes; explicit proxy configuration; encrypted DNS.
- Execution risk: low; the replies are sent only when a client asks.
- Implementation notes: reuses the DHCP Spoofing reply and adds `extra_options` to the rogue server configuration. Values are validated when the configuration is built.
- Lab validation: `scripts/lab/dhcp_option_manipulation_lab.sh` validates reception of the WPAD option. Not yet validated on a MikroTik client or another client's handling.

## DHCP Relay / Option 82 Abuse 🔨

- Protocol: DHCPv4 relay agent information (RFC 3046, Option 82), with circuit ID (sub-option 1) and remote ID (sub-option 2).
- Technical reference: RFC 3046.
- Requirements: a network where the server or relay trusts client-supplied Option 82; the circuit ID the server uses for pool selection.
- Compatibility: servers that select pools by circuit ID or remote ID (the lab uses dnsmasq tags).
- Expected behavior: the server offers an address from the pool of the circuit the client named.
- Evidence: the lab reads the offered address with no Option 82 and with a forged circuit ID.
- Impact: a client receives addresses meant for another port, and can reach or occupy addresses in another part of the network.
- Mitigations: relays that replace client-supplied Option 82; pool selection tied to the port identity from the switch; DHCP snooping on access ports.
- Execution risk: low; one DISCOVER per message, sent once each.
- Implementation notes: builds DISCOVER messages with the forged Option 82; dry run builds them without sending.
- Lab validation: `scripts/lab/dhcp_relay_option82_lab.sh` validates the server's pool choice on dnsmasq. Not yet validated on a MikroTik or a real relay agent.

## Rogue DHCPv6 Server 🔨

- Protocol: DHCPv6 (RFC 8415): SOLICIT, ADVERTISE, REQUEST, REPLY; options IA_NA (3), DNS servers (23), domain search (24), server preference (7).
- Technical reference: RFC 8415 (obsoletes RFC 3315); RFC 3646 (DNS and domain search options).
- Requirements: an attacker on the client's link; the link-local address and MAC of the attacker's interface.
- Compatibility: DHCPv6 clients that accept the first advertisement with the highest preference.
- Expected behavior: the client accepts the rogue advertisement and requests the offered address; the rogue server replies with its DNS servers.
- Evidence: packets built and parsed with Scapy in unit tests. The lab script reports inconclusive on this kernel (no IPv6 in namespaces).
- Impact: a client uses the attacker's DNS servers and search domains.
- Mitigations: DHCPv6 guard on access ports; RA Guard; monitoring for unexpected DHCPv6 servers.
- Execution risk: low; replies only to clients that send messages.
- Implementation notes: no rapid commit (option 14) and no renew/rebind handling; the server answers SOLICIT and REQUEST only.
- Lab validation: not yet validated; needs a Linux machine with IPv6 or a MikroTik DHCPv6 client.

## DHCPv6 Starvation 🔨

- Protocol: DHCPv6 (RFC 8415): SOLICIT, ADVERTISE, REQUEST, REPLY; IA_NA.
- Technical reference: RFC 8415 (SOLICIT and multicast to ff02::1:2, All_DHCP_Relay_Agents_and_Servers).
- Requirements: an attacker on the client's link; the server must hand out IA_NA addresses from a finite pool.
- Compatibility: DHCPv6 servers that create a binding for each client identity (the lab uses dnsmasq).
- Expected behavior: each completed exchange uses one address from the pool; once the pool is empty, legitimate clients get no address.
- Evidence: packet construction and parsing tested with Scapy. The lab script reports inconclusive on this kernel (no IPv6 in namespaces).
- Impact: a denial of IPv6 addressing for legitimate clients on the segment.
- Mitigations: DHCPv6 snooping with a binding limit per port; pool sizes sized to the segment; monitoring of pool use.
- Execution risk: medium; with Solicits set to 0 the attack runs until stopped and keeps using the pool.
- Implementation notes: client identities are random DUID-LLT values with random IAIDs; a MAC-derived link-local address is used as the source. Pending exchanges are capped at 10,000.
- Lab validation: not yet validated; needs a Linux machine with IPv6 or a MikroTik DHCPv6 server.

## LACP Spoofing ✅

- Protocol: IEEE 802.1AX LACPDU (Slow Protocols, EtherType 0x8809, subtype 1).
- Technical reference: IEEE 802.1AX, Link Aggregation Control Protocol.
- Requirements: root or `CAP_NET_RAW` on the link to the aggregate under test, and an authorized test network.
- Compatibility: aggregates that accept LACPDUs from any port. The lab uses the Linux bonding driver in 802.3ad mode.
- Expected behavior: the aggregate reports the claimed system ID as its partner and may add the port to a bundle. An aggregate that ignores LACPDUs from ports without a configured partner keeps no partner.
- Evidence: the bond's partner MAC in `/proc/net/bonding/bond0` before and after the attack, with a control phase that sends nothing.
- Impact: the attacker's port can join an aggregate and take part in its traffic distribution.
- Mitigations: LACP only on ports configured for it; disable LACP on access ports; monitoring of aggregate membership changes.
- Execution risk: low; a fixed number of LACPDUs at a fixed interval.
- Implementation notes: LACPDUs are sent to the Slow Protocols address with the claimed actor fields and an empty partner. Dry run builds the frames without sending them.
- Lab validation: `scripts/lab/lacp_spoofing_lab.sh` validated the partner reported by the bond on Ubuntu (VM), exit 0. Vendor aggregates are not validated.

## IGMP Spoofing 🧪

- Protocol: IGMPv2 membership report (RFC 2236) and IGMP snooping.
- Technical reference: RFC 2236, section 3 (membership report); IGMP snooping as implemented by layer 2 switches.
- Requirements: root or `CAP_NET_RAW` on an interface attached to the segment with the switch; at least one IPv4 multicast group outside 224.0.0.0/24.
- Compatibility: switches that snoop IGMP and trust reports from any port. The lab uses the Linux bridge with multicast snooping.
- Expected behavior: the switch adds the reporting port to the group and forwards the group's traffic there. A switch that limits groups per port, or that filters reports, does not learn the group.
- Evidence: the bridge's membership table for the group before and after one report from the attacker's port.
- Impact: the attacker receives multicast traffic for groups it did not ask for, and can keep a port in a group.
- Mitigations: limits on groups per port; filtering of IGMP reports on access ports; snooping that tracks querier ports; logging of membership changes.
- Execution risk: low; one report per group and count, no traffic flood.
- Implementation notes: reports are IGMPv2 with TTL 1 and the router-alert option, sent to the group's MAC address. The source IP may be 0.0.0.0. Dry run builds the reports without sending them. Groups in 224.0.0.0/24 are refused.
- Lab validation: `scripts/lab/igmp_spoofing_lab.sh` validates the learned membership entry on the attacker's port. Delivery of the group's traffic is not validated on this kernel, and nothing is validated on a vendor switch. Result on an OrbStack Ubuntu VM: PASS (no entry for 239.1.2.3 on the attacker's port before the report; one unauthenticated IGMP report from that port made the bridge learn the group there).

## IGMP Leave Spoofing 🧪

- Protocol: IGMPv2 leave group (RFC 2236) and IGMP snooping.
- Technical reference: RFC 2236, section 3 (leave group, sent to 224.0.0.2); IGMP snooping as implemented by layer 2 switches.
- Requirements: root or `CAP_NET_RAW` on an interface attached to the segment with the switch; at least one IPv4 multicast group outside 224.0.0.0/24.
- Compatibility: switches that snoop IGMP and act on leaves without checking that the sender joined. The lab uses the Linux bridge with multicast snooping.
- Expected behavior: the switch removes the group from the port the leave arrives on, after its leave handling. A switch that checks the sender's membership, or that keeps the group while other hosts report it, does not drop the group.
- Evidence: the bridge's membership table for the group on the shared port, before the leave and after it, with a control period in which no leave is sent.
- Impact: hosts that stay joined behind the same port stop receiving the group until they report again.
- Mitigations: membership tracking per host where the switch allows it; checks that the leaving host joined; fast-leave disabled on shared ports; monitoring of leave messages.
- Execution risk: low; one leave per group and count, no traffic flood.
- Implementation notes: leaves are IGMPv2 with TTL 1 and the router-alert option, sent to 224.0.0.2. Dry run builds the messages without sending them. Groups in 224.0.0.0/24 are refused.
- Lab validation: `scripts/lab/igmp_leave_spoofing_lab.sh` validates the removal on the Linux bridge only. Vendor switches are not validated. Result on an OrbStack Ubuntu VM: PASS (the victim's membership stayed 6 s with no leave; after one leave from a host that never joined the group, the bridge removed the group from the shared port within 2 s).

## LLDP-MED Policy Spoofing 🧪

- Protocol: LLDP (IEEE 802.1AB) with the LLDP-MED extension (ANSI/TIA-1057), network policy TLV.
- Technical reference: ANSI/TIA-1057, network policy TLV (application type, U/T/X flags, VLAN ID, L2 priority, DSCP); IEEE 802.1AB.
- Requirements: root or `CAP_NET_RAW` on an interface attached to the segment with the endpoint; an authorized test network.
- Compatibility: endpoints that accept LLDP-MED network policies from any port. The lab uses lldpd as the receiver, which stores the policy.
- Expected behavior: a vulnerable endpoint or receiver stores the forged policy and applies its VLAN, priority or DSCP. A receiver that accepts policies only from trusted ports, or that ignores LLDP-MED from access ports, does not.
- Evidence: the receiver's stored network policy before and after the advertisements, with the VLAN, priority and DSCP compared to the values sent.
- Impact: an endpoint sends its traffic on a VLAN the attacker chose, or with a different priority, which can carry it into a network it should not reach.
- Mitigations: accept LLDP-MED policies only on trusted ports; set the policy on the switch and not from the endpoint's own LLDP; alerts on policy changes.
- Execution risk: low; a few advertisements, no traffic flood.
- Implementation notes: advertisements go to the nearest bridge address with the MED capabilities TLV and the policy TLV. The policy field is 24 bits after the application type. Dry run builds the frames without sending them.
- Lab validation: `scripts/lab/lldp_med_policy_spoofing_lab.sh` validates the stored policy in lldpd. The endpoint's use of the policy is not validated. Result on an OrbStack Ubuntu VM with lldpd 1.0.18: PASS (no stored policy before the advertisements; after 3 forged advertisements, a voice policy with VLAN 20, priority 5 and DSCP 46, as sent).

## BPDU Guard Trigger Abuse 🧪

- Protocol: IEEE 802.1D configuration BPDU, with BPDU Guard on ports that should not see spanning tree.
- Technical reference: IEEE 802.1D (BPDU reception); vendor documentation for BPDU Guard and err-disable.
- Requirements: root or `CAP_NET_RAW` on an interface attached to the segment with the protected port; an authorized test network.
- Compatibility: switches with BPDU Guard, such as Cisco and the Linux bridge (`bridge link set guard on`). The lab uses the Linux bridge.
- Expected behavior: a protected port that receives a BPDU is disabled, and the host behind it loses connectivity until the port is re-enabled.
- Evidence: the protected port's state before the BPDUs and after them, with BPDU Guard off as a control.
- Impact: a host on a protected port is taken off the network by one device on its segment.
- Mitigations: BPDU Guard with an error-disable recovery timer; root guard on uplinks; port security on access ports; monitoring of err-disabled ports.
- Execution risk: low for the lab; on production it disables a port, so **Destructive Lab** only.
- Implementation notes: BPDUs are configuration BPDUs claiming root priority 0, sent once each; dry run builds them without sending them.
- Lab validation: `scripts/lab/bpdu_guard_trigger_abuse_lab.sh` validates the port state on the Linux bridge. Vendor err-disable behavior is not validated. Result on an OrbStack Ubuntu VM: PASS (with BPDU Guard off, the port stayed forwarding after 3 BPDUs; with BPDU Guard on, the same BPDUs disabled it).

## Unauthorized Mini-Switch / Hub 🧪

- Protocol: IEEE 802.1X on the authenticator port, and Ethernet behavior of hubs and unmanaged switches behind it.
- Technical reference: IEEE 802.1X (port-based authentication, one supplicant per port); IEEE 802.1D MAC learning.
- Requirements: root or `CAP_NET_RAW` on an interface attached to the authorized port (or the mini-switch's port); the MACs of the devices behind the mini-switch, given by the operator; an authorized test network.
- Compatibility: switches and authenticators that check only the first MAC on a port, or that allow several MACs per port without a limit. The lab uses the Linux bridge, which learns every MAC it sees.
- Expected behavior: a port with a one-MAC limit or 802.1X single-host mode takes a violation action on the second MAC. A port that allows several MACs carries every device behind the mini-switch.
- Evidence: the MACs learned on the access port with the authorized device alone, and with the mini-switch passing three devices.
- Impact: devices behind an unmanaged switch use an authorization meant for one host, without being checked.
- Mitigations: port security with a maximum of one MAC; 802.1X single-host mode with the authenticator checking every MAC; physical checks on edge ports.
- Execution risk: low; one frame per listed MAC, to the broadcast address.
- Implementation notes: the operator lists at least two distinct client MACs (up to 16). Frames carry the client MAC as the source, with a fixed payload. Dry run builds them without sending them. This module differs from port security exhaustion: the MACs are the operator's, not random, and the aim is to see whether the port carries several clients.
- Lab validation: `scripts/lab/unauthorized_mini_switch_lab.sh` validates the MACs learned on the access port of the Linux bridge. The port limit and the violation action are not validated. Result on an OrbStack Ubuntu VM: PASS (1 MAC learned on the access port with only the authorized device; 3 MACs learned on the same port behind the mini-switch).

## Private VLAN Isolation Bypass 🧪

- Protocol: IEEE 802.1Q private VLANs (isolated and promiscuous ports), and IPv4 routing through a promiscuous device.
- Technical reference: vendor documentation for private VLANs (isolated, community and promiscuous port types); IEEE 802.1Q.
- Requirements: root or `CAP_NET_RAW` on the attacker's isolated port; the target's MAC and IPv4 address; for the bypass, the promiscuous device's MAC; an authorized test network.
- Compatibility: switches with private VLANs, and the Linux bridge's `isolated` port flag. The lab uses the Linux bridge with a forwarding router.
- Expected behavior: frames between two isolated ports are dropped. A promiscuous device that routes or relays them carries the traffic, so the isolation does not hold against it.
- Evidence: the probes received by the target with direct delivery, and with delivery through the relay.
- Impact: an isolated host reaches another isolated host, which defeats the isolation meant to stop host-to-host traffic.
- Mitigations: restrict the promiscuous device's forwarding and filters; proxy ARP off; ACLs between isolated ports and the uplink; monitoring of traffic that hairpins through the relay.
- Execution risk: low; a few probes, no flood.
- Implementation notes: probes are UDP from the operator's address to the target's address, sent direct or to the relay's MAC. Dry run builds them without sending them.
- Lab validation: `scripts/lab/private_vlan_bypass_lab.sh`, on an OrbStack Ubuntu VM. Result: PASS.
  - Control: with both ports isolated, the victim receives none of the 5 direct probes.
  - Bypass: the probes sent to a promiscuous relay, which forwards them to the victim, reach it 5 of 5.
  - Scope: the isolation holds between isolated ports, but not against a promiscuous device that forwards. The relay's own filters and a vendor's private VLAN configuration are not tested here.

## PPPoE Discovery Flooding 🧪

- Protocol: PPPoE Discovery (RFC 2516, EtherType 0x8863): PADI, PADO, PADR, PADS.
- Technical reference: RFC 2516; rp-pppoe documentation for `pppoe-server`.
- Requirements: root or `CAP_NET_RAW` on the attacker's port; an authorized test network with an access concentrator.
- Compatibility: access concentrators that answer broadcast PADI frames (most do). The lab uses `pppoe-server` from rp-pppoe.
- Expected behavior: a concentrator that rate-limits discovery, or that limits sessions per port and per MAC, answers fewer PADI frames, and a legitimate client keeps its PADO.
- Evidence: the number of PADI frames sent, the number of PADO replies the attacker's port receives, and whether a legitimate probe gets a PADO before and after the flood.
- Impact: the concentrator answers and reserves work for each discovery request, which can slow it and fill its state. Session pool exhaustion, the main impact in the theory, is not measured.
- Mitigations: rate limits on PADI per port; session limits per port and per MAC; discovery monitoring; access ports that accept PPPoE only from authorized customers.
- Execution risk: medium; one broadcast frame per PADI, at the operator's chosen count (up to 1000). No PADR, so no session is opened.
- Implementation notes: frames are PADI with no tags, from a random MAC per frame or a fixed MAC the operator gives. Dry run builds them without sending them. The module never sends PADR: a PADR must echo the concentrator's AC-Cookie tag, which needs the PADO, and a PADR without it gets no PADS.
- Lab validation: `scripts/lab/pppoe_discovery_flooding_lab.sh`, on an OrbStack Ubuntu VM with the `pppoe` package, using `pppoe-server` on a Linux bridge. Result: PASS.
  - Baseline: the concentrator answers a probe with a PADO.
  - Flood: the concentrator answers 200 of 200 PADI frames sent from random client MACs.
  - After the flood: the probe still gets a PADO.
  - Scope: session pool exhaustion and vendor session limits are not measured. The lab sends no PADR, so no session is opened.

## Rogue PPPoE Access Concentrator 🧪

- Protocol: PPPoE Discovery (RFC 2516, EtherType 0x8863): PADI, PADO, PADR, PADS; AC-Cookie and Service-Name tags.
- Technical reference: RFC 2516; rp-pppoe documentation for `pppoe-server`.
- Requirements: root or `CAP_NET_RAW` on the attacker's port; an authorized test network with a PPPoE client segment.
- Compatibility: clients that take the first PADO they receive. The lab uses `pppoe-server` as the legitimate concentrator and a Linux bridge.
- Expected behavior: clients that check the concentrator's name, or that are configured for a specific concentrator, ignore an unexpected PADO. A concentrator that authenticates itself would not complete the session with the rogue.
- Evidence: the PADO the client chooses, the PADS it receives and from which concentrator; the number of trials in which the rogue's PADO arrives first.
- Impact: a client sets its session up with an attacker-controlled concentrator, which sees its session traffic and any PPP authentication that follows.
- Mitigations: client configuration that names the concentrator; access-port controls that accept PADO only from the uplink (PPPoE filtering on the access switch); monitoring of PADO from unexpected ports.
- Execution risk: medium; the module answers every PADI on the segment while it runs, so it must be stopped when the test ends.
- Implementation notes: the module answers PADI with a PADO carrying a new AC-Cookie and the client's Service-Name, and answers a PADR with a PADS only when it carries the cookie issued to that client's MAC (single use). It does not run PPP, so it does not capture PAP or CHAP.
- Lab validation: `scripts/lab/rogue_pppoe_access_concentrator_lab.sh`, on an OrbStack Ubuntu VM with `pppoe-server` on a Linux bridge. Result: PASS.
  - Control: with only the legitimate server, the client's session is with it in 10 of 10 trials.
  - Handshake: when the client takes the rogue's PADO, the rogue completes PADR/PADS in 10 of 10 trials.
  - Silent server: with the legitimate server stopped, the rogue captures 10 of 10 sessions.
  - Race: when the legitimate server is running, the rogue's PADO is first in 0 of 10 trials on this bridge. The race depends on timing and on the legitimate concentrator's response.
  - Not validated: PAP/CHAP credential capture, vendor concentrators and client selection logic.

## EAPOL Start Flooding 🧪

- Protocol: IEEE 802.1X EAPOL (EtherType 0x888E): EAPOL-Start to the PAE group address 01:80:c2:00:00:03; EAP-Request/Identity from the authenticator.
- Technical reference: IEEE 802.1X-2010; RFC 3748 (EAP).
- Requirements: root or `CAP_NET_RAW` on the attacker's port; an authorized test network with an 802.1X authenticator.
- Compatibility: wired 802.1X authenticators that answer EAPOL-Start with an identity request. The lab uses hostapd in wired mode without a RADIUS server.
- Expected behavior: an authenticator with a limit on pending supplicants, a rate limit on EAPOL-Start per port, or a short timeout for unanswered requests, answers fewer Start frames and frees state faster. A legitimate supplicant keeps its identity request.
- Evidence: the number of EAPOL-Start frames sent, the number of distinct supplicants that get an identity request, and whether a legitimate probe gets one before and after the flood.
- Impact: the authenticator creates state and answers each new supplicant, which can use its memory and CPU and delay real clients.
- Mitigations: a limit on pending supplicants per port; rate limits on EAPOL-Start; short timeouts for unanswered requests; port security in addition to 802.1X.
- Execution risk: medium; one frame per supplicant, up to 1000 frames. The module sends no EAP responses, so no authentication completes.
- Implementation notes: frames are EAPOL-Start (version 2) from a random MAC per frame or a fixed MAC the operator gives. Dry run builds them without sending them.
- Lab validation: `scripts/lab/eapol_start_flooding_lab.sh` validates that hostapd answers each of 200 supplicants with an identity request, and that a legitimate probe still gets one. Authenticator state, limits and vendor behavior are not validated. Result on an OrbStack Ubuntu VM with hostapd 2.11: PASS (200 of 200 supplicants got an identity request; the probe got one before and after the flood).

## EAPOL Logoff Spoofing 🧪

- Protocol: IEEE 802.1X EAPOL (EtherType 0x888E): EAPOL-Logoff to the PAE group address 01:80:c2:00:00:03; the authenticator's port state for the supplicant MAC.
- Technical reference: IEEE 802.1X-2010 (logoff and port state); RFC 3748 (EAP).
- Requirements: root or `CAP_NET_RAW` on the attacker's port; the supplicant's MAC; an authorized test network with an 802.1X authenticator and an authenticated supplicant.
- Compatibility: wired 802.1X authenticators that accept EAPOL-Logoff from the source MAC without further checks. The lab uses hostapd in wired mode with FreeRADIUS.
- Expected behavior: an authenticator that ignores EAPOL-Logoff unless it comes from the authorized port, or that requires a cryptographic check on the supplicant, does not deauthorize the victim. A logoff from a MAC that has no session changes nothing.
- Evidence: the number of logoffs sent; the supplicant's disconnect events on the authenticator, with and without spoofed logoffs.
- Impact: a legitimate supplicant is removed from the port and must re-authenticate, which interrupts its access.
- Mitigations: authenticators that check the logoff source against the session and port; MAC-based port security; short re-authentication periods so an attacker's logoff does not last; monitoring of logoffs that do not match a session.
- Execution risk: low; a few frames to the PAE group address, with the victim's MAC as the source.
- Implementation notes: frames are EAPOL-Logoff (version 2) with the operator's given MAC as the source. Dry run builds them without sending them. The module does not send EAP frames, so it does not authenticate.
- Lab validation: `scripts/lab/eapol_logoff_spoofing_lab.sh` validates the victim's disconnect after logoffs that claim its MAC, and the absence of disconnects in the two controls. Vendor authenticators and the data-plane effect are not validated. Result on an OrbStack Ubuntu VM with FreeRADIUS, hostapd 2.11 and wpa_supplicant (EAP-MD5): PASS (0 disconnects in both controls; 1 disconnect after 3 logoffs that claimed the victim's MAC).

## EAPOL Replay 🧪

- Protocol: IEEE 802.1X EAPOL (EtherType 0x888E) and EAP (RFC 3748): EAP responses from the supplicant to the authenticator's requests.
- Technical reference: IEEE 802.1X-2010; RFC 3748 (EAP), including the identifier and the challenge in EAP-MD5.
- Requirements: root or `CAP_NET_RAW` on the attacker's port in promiscuous mode, to capture the supplicant's responses; the supplicant's MAC; an authorized test network with an 802.1X authenticator.
- Compatibility: authenticators that do not check the identifier or the session state of a response. The lab uses hostapd in wired mode with FreeRADIUS and EAP-MD5.
- Expected behavior: an authenticator that accepts an EAP response only as the answer to its latest request, for the current session, does not reopen the port on a replayed response. A fresh start from the same MAC still starts a new exchange.
- Evidence: the number of responses captured and replayed; the authenticator's log lines for the supplicant and RADIUS requests around the replay, compared with a control.
- Impact: a captured authentication exchange can be used again to obtain access on a port, if the authenticator accepts it.
- Mitigations: check the EAP identifier and state on every response; fresh challenges per session (EAP-MD5 without a fresh challenge is weak); short re-authentication periods; EAP methods with mutual authentication and key derivation (EAP-TLS, PEAP).
- Execution risk: low; the module sends the captured responses, a few frames, and sends no new EAP responses.
- Implementation notes: the module captures the victim's EAP responses (code 2) during the capture window, then sends each one `repeats` times. Dry run builds nothing and sends nothing. Captures need promiscuous mode on the attacker's port.
- Lab validation: `scripts/lab/eapol_replay_lab.sh` validates that the replayed responses produced no activity in this configuration, against a control in which a fresh EAPOL-Start from the same MAC is processed. Vendor authenticators, replay during an active exchange and other EAP methods are not validated. Result on an OrbStack Ubuntu VM with FreeRADIUS, hostapd 2.11 and wpa_supplicant (EAP-MD5): PASS (2 captured responses replayed with no hostapd or RADIUS activity; a fresh EAPOL-Start from the same MAC produced 2 hostapd lines).

## 802.1X Identity Spoofing 🧪

- Protocol: IEEE 802.1X EAPOL (EtherType 0x888E) and EAP (RFC 3748): EAP-Request/Identity from the authenticator and EAP-Response/Identity from the supplicant; RADIUS Access-Request with User-Name.
- Technical reference: IEEE 802.1X-2010; RFC 3748 (EAP); RFC 3579 (RADIUS support for EAP).
- Requirements: root or `CAP_NET_RAW` on the attacker's port, with promiscuous capture to read the identity request; an authorized test network with an 802.1X authenticator and an authentication server.
- Compatibility: authenticators that pass the identity from the supplicant to the authentication server before any credential is checked, which is the standard behavior. The lab uses hostapd in wired mode with FreeRADIUS.
- Expected behavior: the authenticator forwards the claimed identity, and the server decides. A server that issues a challenge only for known identities, and rejects unknown ones without a credential, grants no session. A server policy that grants access by name alone, or by MAC-based fallback, is the risk to test.
- Evidence: the identity requests seen and answered, and the RADIUS requests for each claimed User-Name, with the challenges, accepts and rejects the server sends back.
- Impact: a claimed identity drives the server's policy (for example VLAN assignment or group rules) before the supplicant has proven it.
- Mitigations: EAP methods with mutual authentication (EAP-TLS, PEAP with server validation); server policies that require a credential for every identity; no fallback to MAC authentication for names that have a credential; monitoring of identities that never complete.
- Execution risk: low; one exchange per identity, a few frames, no EAP method completed.
- Implementation notes: the module sends EAPOL-Start, waits for the identity request, then answers with the claimed identity and the request's identifier. With no source MAC given, each identity uses a random MAC. Dry run builds nothing and sends nothing. The module never sends a credential.
- Lab validation: `scripts/lab/eapol_identity_spoofing_lab.sh` validates that bob and alice reach RADIUS unverified, with an EAP-MD5 challenge each and no Access-Accept, against a control with no identity answer. Server policies that grant by name, and vendor authenticators, are not validated. Result on an OrbStack Ubuntu VM with FreeRADIUS, hostapd 2.11: PASS (bob and alice each reached RADIUS unverified and got an EAP-MD5 challenge, 0 Access-Accept; the control sent no RADIUS request).

## Redirect Spoofing 🧪

Forged ICMPv6 Redirect messages (RFC 4861, section 4.5) that make a victim host route traffic for an off-link destination through the attacker.

### Implementation notes

- `src/macabre/attacks/redirect_spoofing.py` builds one Redirect per frame. The IPv6 source is the router's link-local address, the hop limit is 255, the Target Link-Layer option carries the attacker's MAC, and the Redirected Header option carries the original packet.
- The Redirected Header option is included by default (`include_redirected_header=True`), as RFC 4861 asks.

### Lab validation

Lab: `scripts/lab/redirect_spoofing_lab.sh`, on Linux with network namespaces (router, victim and attacker on one bridge).

- Setup: the victim takes the legitimate router as its default route and gets an address in the advertised prefix.
- Control: before the attack, the victim's next hop for the destination is the router.
- Attack, without the Redirected Header option: three Redirects from the attacker. The victim's next hop for the destination changes to the attacker's link-local address. Result: validated on Linux 7.2.9.
- Attack, with the Redirected Header option (the RFC default): the victim counts the Redirects (`Icmp6InRedirects` 3) and rejects them (`Icmp6InErrors` 3). The next hop does not change. The kernel check that rejects them has not been identified. `tcpdump` shows the packet is well formed: valid ICMPv6 checksum, correct option lengths.

Limitation: on this kernel the effect needs `include_redirected_header=False`. With the RFC default the route does not change. The lab sets the option explicitly. The GUI panel uses the default and has not been checked against this kernel.

## STP Loop Induction 🧪

Connecting two switch ports through an attacker bridge that runs no Spanning Tree, so the switch sees both ports as forwarding and a loop forms.

### Implementation notes

- `src/macabre/attacks/stp_loop_induction.py` builds the attacker bridge with STP off (`stp_state 0`) and drops the STP group address (`01:80:c2:00:00:00`) with an nftables bridge rule. Without the rule, Linux relays the switch's own BPDUs back on the second port, the switch blocks that port, and no loop forms.
- `run_stp=True` builds the control: the bridge runs STP, blocks one of its own ports, and no BPDU rule is installed.
- The module holds the bridge until it receives SIGINT or SIGTERM, then removes the bridge and the rule. It runs as `python -m macabre.attacks.stp_loop_induction a1 a2` inside the attacker's namespace.

### Lab validation

Lab: `scripts/lab/stp_loop_induction_lab.sh`, on Linux with network namespaces (switch, attacker and host), run on an OrbStack Ubuntu VM. Result: PASS.

- Control (`--run-stp`): the attacker bridge runs STP and blocks one of its own ports. The switch ports stay in `forwarding`, and the RX packet counters on the switch ports over 20 s stay near zero (p1 = 2, p2 = 0). No loop forms.
- Attack: the bridge runs no STP and drops STP BPDUs. Both switch ports stay in `forwarding`, and the RX packet counters over 20 s are 26,403,944 on p1 and 46,312,342 on p2. The loop is sustained.
- The traffic in the loop is background control traffic from the namespaces' own interfaces: IPv6 router solicitations and MLD reports with IPv6 enabled, IGMPv3 reports to 224.0.0.22 with IPv6 disabled. It is not the injected frame. The lab's criterion is the RX counters, so this background does not change the verdict.
- A broadcast injected with the host's own MAC as source did not multiply: one copy per port. With a different source MAC, the same broadcast became about 17 million copies at the switch ports in 25 s, on the same topology (diagnostic run). The loop was never the limit: the cause is the source MAC the host used, not the loop.
- Without the BPDU drop rule, the switch sees its own BPDUs on the second port and blocks it. No loop forms. Observed in the prototype.
- In the prototype's control run, one switch port was in `blocking`. In the lab run, both were in `forwarding`. The lab criterion does not depend on that state.

Not tested: RSTP, MSTP and PVST+, and real switches.

## STP Priority Manipulation 🧪

A bridge that advertises a lower bridge priority than the switch, with the same root path cost, wins the designated port election on a shared segment. The switch's port on that segment then blocks.

- **Protocol**: IEEE 802.1D configuration BPDU, with a bridge ID lower than the switch's on a shared segment.
- **Technical reference**: IEEE 802.1D-2004 (designated port selection).
- **Requirements**: root or `CAP_NET_RAW` on a port of the shared segment, and an authorized test network.
- **Compatibility**: switches running STP on the segment. Ports with BPDU Guard shut down on the first BPDU instead of blocking.
- **Expected behavior**:
  - Vulnerable: the switch's port stops being designated and blocks while the attacker's BPDUs are received.
  - Protected: root guard on ports facing other bridges, BPDU Guard on access ports, or other limits on superior BPDUs.
- **Evidence**: the state of the switch's port on the shared segment during the baseline, the control and the attack, the switch's root port, and the recovery after the attacker stops.
- **Impact**: a blocked port cuts off the hosts behind it on that segment.
- **Mitigations**: root guard on ports facing other bridges, and BPDU Guard on access ports.
- **Execution risk**: **Active Test** on an authorized port, on a test topology.

### Implementation notes

- Frames carry the real root ID and root path cost, read from the switch, and a bridge priority set by the operator.
- The module does not take the root. It only tries to win the designated port of the shared segment.

### Lab validation

`scripts/lab/stp_priority_manipulation_lab.sh`, on an OrbStack Ubuntu VM. Result: PASS.

- Baseline: the switch's port on the shared segment is forwarding.
- Control (priority 61440): the port stays forwarding.
- Attack (priority 0): the port is blocking for the whole run.
- Recovery: the port forwards again after the attacker stops, and the switch's root port stays on the real root.

Not tested: RSTP, MSTP, PVST+ and real switches.

## L2 Loop Amplification 🧪

Sending one broadcast or multicast frame into a loop and counting how many copies come back, so an audit can measure how much a single frame can cost a bridged network without loop protection.

### Implementation notes

- `src/macabre/attacks/l2_loop_amplification.py` sends frames with a random unicast source MAC per frame, the requested broadcast or multicast destination, and the experimental EtherType `0x88B5`. It never uses the sender's own MAC: a host's MAC learned on a port of the loop stopped the copies in the lab.
- The module reports frames sent. The factor is measured outside the module: `amplification_factor` gives copies per injected frame from a count taken at the switch.
- The lab reuses the STP loop built by `macabre.attacks.stp_loop_induction`: with STP on it is the control, without STP it is the attack.

### Lab validation

Lab: `scripts/lab/l2_loop_amplification_lab.sh`, on Linux with network namespaces (switch, attacker and sender), run on an OrbStack Ubuntu VM. Result: PASS.

- Baseline (one link, no loop): 1 copy per injected frame in 20 s.
- Control (two links, STP on in the switch and in the attacker bridge): 2 copies per injected frame. The switch ports stay in `forwarding`; the attacker bridge blocks its own port, so no loop forms.
- Attack (two links, no STP, STP BPDUs dropped at the attacker bridge): 1,215,284 copies per injected frame in 20 s. The loop multiplies one frame.
- Copies are counted with `tcpdump -Q in` on the switch ports, filtered by the injected destination. Background control traffic (IGMP, IPv6 router solicitations, MLD) does not match that destination and is not counted.
- The sender uses a random source MAC. With the host's own MAC as source, one broadcast did not multiply on the same topology (diagnostic run). See the STP Loop Induction note.

Not tested: real switches and their loop protection (RSTP, MSTP, storm control).

## Neighbor Solicitation Spoofing 🧪

Sends forged Neighbor Solicitations (RFC 4861) whose IPv6 source and NS target are the impersonated address and whose Source Link-Layer Address option is the operator's MAC. A host that receives an NS with that option records the link-layer address for the source without any reply, so the attack needs no response from the victim. The destination is the solicited-node group of the receiver when one is given, otherwise the group of the target. Only hosts that join that group receive the frame, so a victim that does not own the target must be named as receiver.

Distinct from NDP Cache Poisoning, which sends unsolicited Neighbor Advertisements with the Override flag. This technique relies on the NS path only.

### Implementation notes

- Module: `src/macabre/attacks/neighbor_solicitation_spoofing.py`. Frame: `Ether(src=source, dst=33:33:ff:xx:xx:xx) / IPv6(src=target, dst=ff02::1:ffxx:xxxx, hlim=255) / ICMPv6ND_NS(tgt=target) / ICMPv6NDOptSrcLLAddr(lladdr=source)`.
- Solicited-node address and MAC are computed per RFC 4291 (low 24 bits of the address, `33:33` plus the low 32 bits).
- Unit tests: `tests/test_neighbor_solicitation_spoofing.py` (15 tests).
- Lab script: `scripts/lab/neighbor_solicitation_spoofing_lab.sh`. Victim, server and attacker share one bridge. Control: the victim pings the server, and its cache holds the server's MAC. Attack: the attacker sends NSs to the victim, and the entry must change to the attacker's MAC.

### Lab validation

Lab: `scripts/lab/neighbor_solicitation_spoofing_lab.sh`, on Linux with network namespaces (victim, server, attacker on one bridge), run on an OrbStack Ubuntu VM. Result: PASS.

- Control (victim pings the server): the victim's entry for the server holds the server's MAC.
- Attack, empty cache (the verdict; the victim never pinged the server): after three forged NSs the entry holds the attacker's MAC.
- Attack on a STALE entry and on a REACHABLE entry (informational): the attacker's MAC replaces the server's MAC in both states.

The NS must ask for one of the victim's own addresses. An earlier version of the module asked for the server's address, and the victim discarded the NS: the cache showed no change in any phase. The module now sends the NS with the impersonated address as IPv6 source, the victim's address as target, and the victim's solicited-node group as destination.

Not tested: switches with NDP inspection or a RA guard, and hosts other than Linux.

## Duplicate Address Detection DoS 🧪

Answers the Duplicate Address Detection (DAD) of a new host with forged Neighbor Advertisements for the address it is about to configure (RFC 4862). A host that receives an NA for its tentative address marks the address as duplicate and does not use it.

### Implementation notes

- Module: `src/macabre/attacks/duplicate_address_detection_dos.py`. Frame: `Ether(src=operator, dst=33:33:00:00:00:01) / IPv6(src=link-local of operator, dst=ff02::1, hlim=255) / ICMPv6ND_NA(tgt=target, S=0, O=1) / ICMPv6NDOptDstLLAddr(lladdr=operator)`.
- Sends `frames` NAs, `interval` seconds apart. The default burst (30 NAs at 0.1 s) covers the DAD window of about 1 to 2 s.
- Unit tests: `tests/test_duplicate_address_detection_dos.py` (15 tests).
- Lab script: `scripts/lab/duplicate_address_detection_dos_lab.sh`. Two hosts on one veth pair. Control: the victim adds a new address with DAD, and it ends up configured. Attack: an NA burst runs while the victim adds the address, and it must end up `dadfailed`.

### Lab validation

Lab: `scripts/lab/duplicate_address_detection_dos_lab.sh`, on Linux with network namespaces (victim and attacker on one veth pair), run on an OrbStack Ubuntu VM. Result: PASS.

- Control (no attacker): the victim adds a new address, DAD finishes, and the address is configured.
- Attack (NA burst during DAD): the address ends with the `dadfailed` flag, so the victim does not use it.

Not tested: real hosts other than Linux, and networks with Neighbor Discovery inspection or DHCPv6 fallback.

## Router Solicitation Flooding 🧪

Sends a stream of Router Solicitations (RS, RFC 4861) to the all-routers group. Each RS makes a router process the message, so a high rate costs the router CPU and can crowd out real traffic.

### Implementation notes

- Module: `src/macabre/attacks/router_solicitation_flooding.py`. Frame: `Ether(src=operator, dst=33:33:00:00:00:02) / IPv6(src=link-local of operator, dst=ff02::2, hlim=255) / ICMPv6ND_RS() / ICMPv6NDOptSrcLLAddr(lladdr=operator)`.
- Sends `frames` RSs, `interval` seconds apart (default 500 at 5 ms).
- Unit tests: `tests/test_router_solicitation_flooding.py` (11 tests).
- Lab script: `scripts/lab/router_solicitation_flooding_lab.sh`. A router namespace with IPv6 forwarding on, and an attacker on one veth pair. The measure is the router's `Icmp6InRouterSolicits` counter in `/proc/net/snmp6`, which the kernel increments for every RS it receives.

### Lab validation

Lab: `scripts/lab/router_solicitation_flooding_lab.sh`, on Linux with network namespaces (router with IPv6 forwarding, and attacker on one veth pair), run on an OrbStack Ubuntu VM. Result: PASS.

- Control (no attacker): the router receives 1 RS over 3 s.
- Attack (500 RSs at 5 ms): the router receives 502 RSs during the attack, counted by `Icmp6InRouterSolicits`.

The lab measures the RSs that reach the router, not the router's CPU load or its RA replies. Not tested: routers with RS rate limiting, and access ports with RS filtering.

## Neighbor Advertisement Spoofing 🧪

Answers a host's Neighbor Solicitation for an IPv6 address with a solicited Neighbor Advertisement (RFC 4861) from the operator's MAC. The requester records the first reply it gets. This is the solicited variant, and it is distinct from NDP Cache Poisoning, which sends unsolicited NAs with the Override flag to replace entries that are already valid.

### Implementation notes

- Module: `src/macabre/attacks/neighbor_advertisement_spoofing.py`. Listens for NSs whose target is the configured address, from a unicast source (DAD probes from `::` are not answered here), and replies with `Ether(src=operator, dst=requester MAC) / IPv6(src=target, dst=requester, hlim=255) / ICMPv6ND_NA(tgt=target, S=1, O=0) / ICMPv6NDOptDstLLAddr(lladdr=operator)`.
- The reply has Override clear, so a requester with a valid entry does not replace it on this NA alone. The attack targets requesters that have no valid entry yet.
- Unit tests: `tests/test_neighbor_advertisement_spoofing.py` (16 tests).
- Lab script: `scripts/lab/neighbor_advertisement_spoofing_lab.sh`. Victim, server and attacker on one bridge. Control: the server answers, and the victim's cache holds the server's MAC. Attack: the server is down, the attacker answers the victim's NS, and the entry must hold the attacker's MAC in REACHABLE.

### Lab validation

Lab: `scripts/lab/neighbor_advertisement_spoofing_lab.sh`, on Linux with network namespaces (victim, server and attacker on one bridge), run on an OrbStack Ubuntu VM. Result: PASS.

- Control (server up): the victim's entry for the server holds the server's MAC.
- Attack (server interface down, attacker listening): the attacker answers the victim's NS with a solicited NA, and the entry holds the attacker's MAC in REACHABLE.

Not tested: a requester that already has a valid entry, where the Override-clear reply is expected to be ignored, and hosts other than Linux. Those cases belong to NDP Cache Poisoning, which uses Override.
