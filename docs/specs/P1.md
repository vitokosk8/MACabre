# P1 Specifications

Core techniques (priority P1) from the [attack catalog](../attack-catalog.md). The theory behind each attack, which protocols it abuses and why, is in [docs/attacks](../attacks/README.md). Each technique is specified and implemented one at a time, using the same fields:

- **Protocol**: the protocol or mechanism involved.
- **Technical reference**: standard or documentation.
- **Requirements**: what the audit needs (privileges, access, topology).
- **Compatibility**: devices and configurations where the technique applies.
- **Expected behavior**: what a vulnerable and a protected device do.
- **Evidence**: what MACabre collects to prove the result.
- **Impact**: consequences for the network.
- **Mitigations**: controls that prevent or detect the technique.
- **Execution risk**: the operating mode in which the technique may run.

Status legend: ✅ implemented and lab-validated, ⏳ planned.

## MAC Flooding / CAM Overflow ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1Q, bridge learning and forwarding process. Vendor documentation on port security and MAC address limits.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the switch port under test. Layer 2 reachability to the switch. No other requirements.
- **Compatibility**: switches that learn source MAC addresses dynamically. Most managed and unmanaged switches. Devices with port security or MAC limits may stop learning after their limit, which is the expected protected behavior.
- **Expected behavior**:
  - Vulnerable: the switch learns every random source MAC, and unknown unicast frames are flooded to all ports. The table grows until it is full, and the switch may fail open (flood all traffic).
  - Protected: port security limits the learned addresses on the attacked port, and violations are logged or the port is shut down.
- **Evidence**:
  - Number of addresses learned by the switch (for example, from the bridge forwarding table or the switch CAM table).
  - Number of unknown unicast frames received on a monitored port, compared with the number sent.
  - Switch log entries for port security violations, if available.
- **Impact**: traffic flooding on the segment, loss of confidentiality (other hosts' traffic is delivered to the attacker's port), and degraded network performance.
- **Mitigations**: port security with a maximum number of MAC addresses and a violation action (shutdown or restrict), storm control, and monitoring of MAC table growth.
- **Execution risk**: **Active Test**, with a limited frame count and rate. Sustained high rates in production are **Destructive Lab** only.

### Implementation notes

- Frames use a random source MAC and a random unicast destination MAC, with EtherType `0x88B5` (IEEE 802 local experimental), so hosts ignore the payload.
- The attack sends frames only. It does not verify the switch state; the lab script checks the result from the switch side.
- Limitation: the lab uses a Linux bridge, which has no CAM size limit. It measures address learning and unknown-unicast flooding, not a real CAM overflow.

## MAC Flapping ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1Q, bridge learning and forwarding process. Vendor documentation on MAC move detection and loop protection.
- **Requirements**: root or `CAP_NET_RAW` on two interfaces, each attached to a different port of the same switch (or the same VLAN). Layer 2 reachability to the switch.
- **Compatibility**: switches that relearn a MAC address when it appears on another port. Most managed and unmanaged switches. Switches with MAC move detection or port security may shut the port or log the move, which is the expected protected behavior.
- **Expected behavior**:
  - Vulnerable: the switch moves the target MAC entry between the two ports on every frame. Traffic destined to that MAC is delivered to the wrong port or delayed while the entry flaps.
  - Protected: the switch detects the MAC move, logs it, and keeps the entry on the first port (or shuts the port) after a threshold.
- **Evidence**:
  - Number of entry moves for the target MAC, from the switch side (for example, `bridge monitor fdb` on Linux, or the switch MAC move log).
  - Number of distinct ports used by the target MAC in the switch table.
  - Switch log entries for MAC move or port security violations, if available.
- **Impact**: disruption of unicast traffic to the target MAC, intermittent connectivity, and possible misdelivery of frames during the flapping.
- **Mitigations**: MAC move detection and notification, port security with violation actions, loop and flap protection features, and monitoring of MAC table changes.
- **Execution risk**: **Active Test**, with a limited frame count and rate. Sustained flapping of a production MAC is **Destructive Lab** only.

### Implementation notes

- Both interfaces send frames with the same source MAC (the target). A random target is used when none is given. The source MAC is always unicast (the least significant bit of the first octet is 0).
- Frames alternate between the two interfaces, starting with interface A. Destination MAC is random unicast, and EtherType is `0x88B5` (IEEE 802 local experimental), as in MAC flooding.
- The two interfaces must be different. The GUI and the library reject the same interface for both ports.
- The attack sends frames only. The lab script checks the result from the switch side, counting entry moves with `bridge monitor fdb`.

## MAC Address Spoofing ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1Q, bridge learning and forwarding process. Vendor documentation on MAC move detection and port security.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to a switch port in the same VLAN as the target. Layer 2 reachability to the target's segment. The attacker does not need the target's IP address.
- **Compatibility**: switches that relearn a MAC address when it appears on another port. Most managed and unmanaged switches. Switches with MAC move detection or port security may block the move, which is the expected protected behavior.
- **Expected behavior**:
  - Vulnerable: after the spoofed frames, the switch forwards frames addressed to the target MAC to the attacker's port, and the target stops receiving them.
  - Protected: the switch detects the MAC move, logs it, and keeps the entry on the original port (or shuts the attacker's port) after a violation.
- **Evidence**:
  - Switch port for the target MAC before and after the attack (for example, `bridge fdb show` on Linux, or the switch MAC table).
  - Unicast frames addressed to the target, received by the target and by the attacker, before and after the spoofing.
  - Switch log entries for MAC move or port security violations, if available.
- **Impact**: interception of unicast traffic addressed to the impersonated host, denial of service for that host, and a base for man-in-the-middle attacks when combined with forwarding.
- **Mitigations**: static MAC entries for critical hosts, port security with a violation action, MAC move detection and logging, DHCP snooping and dynamic ARP inspection to limit spoofed identities, and 802.1X on access ports.
- **Execution risk**: **Active Test**, with a limited frame count. Sustained spoofing of a production host is **Destructive Lab** only.

### Implementation notes

- The attack sends frames whose source MAC is the target's address, with destination broadcast and EtherType `0x88B5`. The broadcast destination makes the switch learn the source on the attacker's port without relying on a known unicast destination.
- The target MAC is required and must be unicast. The GUI and the library reject empty, invalid, multicast and broadcast values.
- The attack sends frames only. The lab script checks the switch port and the frames received by each host.

### Lab validation

`scripts/lab/mac_spoofing_lab.sh` builds three isolated test hosts on one software bridge: a sender, the target (MAC `02:00:00:00:00:10`) and the attacker. The last run (20 frames from the sender, 5 spoofed frames):

- Baseline: switch port for the target MAC `sw-t`; target received 20 of 20; attacker received 0 of 20.
- After spoofing: switch port `sw-a`; target received 0 of 20; attacker received 20 of 20.

## MAC Cloning ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding, and IEEE 802.1X or port security access control that admits traffic by MAC address (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1X (port-based access control). Vendor documentation on port security (sticky or static MAC addresses) and MAC-based access lists.
- **Requirements**: root on the attacking host, and a network interface whose hardware address can be changed. Physical or Layer 2 access to a port that admits a known MAC address, and the MAC address of an authorized device on the segment.
- **Compatibility**: ports with MAC-based access control: port security with a static or sticky MAC address, MAC authentication bypass (MAB), and MAC-based allow lists. Ports protected by 802.1X with certificate or user authentication are not affected by a MAC clone alone.
- **Expected behavior**:
  - Vulnerable: the port admits frames from the cloned address, and the attacker gets network access as the authorized device.
  - Protected: the port rejects frames from an unknown MAC, logs the violation, and shuts down the port. Certificate-based authentication (802.1X) prevents access even with the right MAC.
- **Evidence**:
  - Frames sent from the attacking host with the cloned source MAC, and whether they reach a server on the segment.
  - Frames sent with the attacker's own MAC on the same port, to show that the control was active before the clone.
  - Switch log entries for port security violations, if available.
- **Impact**: unauthorized access to the network as an authorized device, bypass of MAC-based access control, and possible misattribution of traffic to the cloned device in logs.
- **Mitigations**: 802.1X with certificate-based authentication, port security with violation shutdown, DHCP snooping and dynamic ARP inspection to tie identity to address bindings, and monitoring for duplicate or moving MAC addresses.
- **Execution risk**: **Active Test**, with a short window of access. Cloning a production device's MAC is **Destructive Lab** only: the cloned device and the attacker both use the address and can disrupt each other.

### Implementation notes

- The module changes the hardware address of the interface with `ip link` (down, set address, up) and keeps it until the attack is stopped. The original address is read before the change and restored in a `finally` block, so it returns even if setting the clone fails midway.
- Unlike spoofing, cloning affects the whole host: the IP stack and every application send with the cloned address.
- A dry run only prints the planned commands and changes nothing.
- Scapy caches interface MAC addresses when it loads. The module does not use Scapy to read the MAC; the lab reads it with `ip` for the same reason.

### Lab validation

`scripts/lab/mac_cloning_lab.sh` uses a Linux bridge as the switch. Its port for the attacker has an nftables rule that drops frames whose source is not the authorized MAC, which emulates port security with one allowed address. The last run (20 frames per phase):

- Phase 1, attacker's own MAC: the server received 0 of 20 frames. The switch dropped them.
- Phase 2, MAC cloning of the authorized MAC: the host presented the authorized MAC, and the server received 20 of 20 frames. After stopping, the attacker's MAC returned to its original address.

## ARP Spoofing ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet.
- **Technical reference**: RFC 826 (Address Resolution Protocol). RFC 5227 (IPv4 address conflict detection), for the unsolicited-reply behavior hosts must handle. Vendor documentation on Dynamic ARP Inspection.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the victim's broadcast domain (VLAN). The victim's IP and, optionally, its MAC address. No other requirements.
- **Compatibility**: IPv4 hosts that update their ARP cache from unsolicited replies. Most operating systems do so for entries they already hold. Hosts with static ARP entries, and switches with Dynamic ARP Inspection enabled, are not affected by the reply.
- **Expected behavior**:
  - Vulnerable: the victim's cache entry for the spoofed IP changes to the attacker's MAC, and the victim sends that IP's traffic to the attacker.
  - Protected: static ARP entries for critical hosts, Dynamic ARP Inspection drops replies that do not match the DHCP snooping binding table, and the host logs or ignores the unsolicited change.
- **Evidence**:
  - The victim's ARP cache entry for the spoofed IP, before and after the attack (for example, `ip neigh show` on Linux or `arp -a` on other systems).
  - Number of forged replies sent by the attacker, and the MAC they claimed.
  - Switch logs for Dynamic ARP Inspection drops, if available.
- **Impact**: man-in-the-middle position for traffic to the spoofed IP, interception or disruption of the victim's connections, and denial of service if the attacker does not forward traffic.
- **Mitigations**: Dynamic ARP Inspection with DHCP snooping, static ARP entries for gateways and servers, port security on access ports, and monitoring for IP-to-MAC changes.
- **Execution risk**: **Active Test**, with a limited number of replies and a short duration. Poisoning production caches is **Destructive Lab** only: it disrupts every host that talks to the spoofed IP.

### Implementation notes

- Replies are sent with the interface's own MAC (read with `ip`, not Scapy's cache), as both the Ethernet and the ARP sender address.
- Without a victim MAC the reply goes to broadcast. A reply addressed to the victim's MAC is more targeted and less visible on the segment.
- The attack sends replies only. It does not forward traffic, so a victim that loses its gateway will notice. Combining it with IP forwarding is out of scope for this module.

### Lab validation

`scripts/lab/arp_spoofing_lab.sh` uses a Linux bridge with a victim, the real gateway and the attacker. The last run:

- Baseline: the victim's cache for `10.95.0.1` held the gateway's MAC `02:00:00:00:00:01`.
- After 10 forged replies: the entry held the attacker's MAC `02:00:00:00:00:30`.

## ARP Cache Poisoning ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet.
- **Technical reference**: RFC 826 (Address Resolution Protocol). RFC 5227 (IPv4 address conflict detection), for the unsolicited-reply behavior hosts must handle. Vendor documentation on Dynamic ARP Inspection.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the victim's and the gateway's broadcast domain (VLAN). The victim's and the gateway's IP addresses; their MAC addresses are optional.
- **Compatibility**: IPv4 hosts that update existing ARP cache entries from unsolicited replies. Hosts with static ARP entries, and switches with Dynamic ARP Inspection, are not affected.
- **Expected behavior**:
  - Vulnerable: the victim's cache for the gateway and the gateway's cache for the victim both point to the attacker's MAC, so traffic in both directions passes through the attacker.
  - Protected: static ARP entries on the victim and the gateway, Dynamic ARP Inspection, and detection of a single IP claimed by a new MAC.
- **Evidence**:
  - The victim's cache entry for the gateway and the gateway's cache entry for the victim, before and after the attack.
  - Number of rounds and forged replies sent, and the MAC they claimed.
  - Switch or host logs for ARP inspection drops or duplicate-IP detection, if available.
- **Impact**: full man-in-the-middle position between two hosts: interception, modification or denial of their traffic, and credential theft from unencrypted sessions.
- **Mitigations**: Dynamic ARP Inspection with DHCP snooping, static ARP entries for critical hosts, port security, 802.1X, encrypted protocols end to end, and monitoring for IP-to-MAC changes.
- **Execution risk**: **Active Test**, with a short duration and a limited number of rounds. Poisoning production hosts is **Destructive Lab** only: it intercepts their live traffic.

### Implementation notes

- Each round sends two replies: one to the victim (gateway IP at the attacker's MAC) and one to the gateway (victim IP at the attacker's MAC). Repeated rounds keep the entries from expiring.
- The attacker's MAC is read with `ip`, not from Scapy's cache.
- The module poisons caches only. It does not forward traffic, so a connection between the victim and the gateway stops working until forwarding is enabled on the attacker. Forwarding is out of scope for this module.
- The difference from ARP spoofing is the scope: ARP spoofing sends one forged binding to one host; cache poisoning poisons both ends and keeps them poisoned.

### Lab validation

`scripts/lab/arp_poisoning_lab.sh` uses a Linux bridge with a victim, the gateway and the attacker. The last run (6 rounds, 12 forged replies):

- Baseline: the victim's cache for the gateway held `02:00:00:00:00:01`, and the gateway's cache for the victim held `02:00:00:00:00:10`.
- After poisoning: both caches held the attacker's MAC `02:00:00:00:00:30`.

## Gratuitous ARP Spoofing ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`). Gratuitous ARP is an unsolicited ARP request whose sender and target IP are the same address.
- **Technical reference**: RFC 826 (Address Resolution Protocol). RFC 5227 (IPv4 address conflict detection), which defines the announcement and the behavior of hosts that receive it.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the segment. The IP address to announce. No victim address is needed.
- **Compatibility**: IPv4 hosts that update existing ARP cache entries from announcements. Most operating systems do so. Hosts with static entries, and switches with Dynamic ARP Inspection, are not affected.
- **Expected behavior**:
  - Vulnerable: every host on the segment that caches the announced IP updates its entry to the attacker's MAC, from a single broadcast.
  - Protected: static ARP entries, Dynamic ARP Inspection, and duplicate-address detection that flags an IP announced by a new MAC.
- **Evidence**:
  - The ARP cache entry for the announced IP on each host, before and after the announcements.
  - Number of announcements sent and the MAC they claimed.
  - Host or switch logs for address conflicts or ARP inspection drops, if available.
- **Impact**: traffic to the announced IP is redirected on the whole segment, which is wider than one victim. Hosts that depend on that IP lose connectivity or send it to the attacker.
- **Mitigations**: Dynamic ARP Inspection with DHCP snooping, static ARP entries for gateways and servers, duplicate-address detection, and monitoring for IP-to-MAC changes.
- **Execution risk**: **Active Test**, with a limited number of announcements. Announcing a production gateway's IP is **Destructive Lab** only: it affects every host on the segment.

### Implementation notes

- The announcement is an ARP request with sender and target IP equal to the announced address, sent to broadcast with the target MAC set to zero. This is the form `arping -A` produces.
- The attacker's MAC is read with `ip`, not from Scapy's cache.
- The difference from ARP spoofing is the scope: spoofing targets one host, and a gratuitous announcement reaches every host that caches the IP.

### Lab validation

`scripts/lab/gratuitous_arp_lab.sh` uses a Linux bridge with two victims, the gateway and the attacker. The last run (3 announcements from one broadcast each):

- Baseline: both victims cached the gateway as `02:00:00:00:00:01`.
- After the announcements: both victims cached `02:00:00:00:00:30`, the attacker's MAC.

## ARP Request Flooding ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet.
- **Technical reference**: RFC 826 (Address Resolution Protocol). Vendor documentation on ARP rate limiting, neighbor table size limits (for example the Linux `gc_thresh` settings) and CoPP.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the segment. The subnet to draw sender and target addresses from. No other requirements.
- **Compatibility**: any IPv4 segment. The effect depends on how many requests the hosts and the router process per second, and on the size of their neighbor tables.
- **Expected behavior**:
  - Vulnerable: every host processes each broadcast request, and the host that owns the target IP answers each sender, so its neighbor table grows with every distinct sender. High rates raise CPU load on the hosts and the router.
  - Protected: ARP rate limiting or control-plane policing on the router, bounded neighbor tables with eviction, and ARP inspection that drops requests from senders the switch did not learn.
- **Evidence**:
  - Requests received by a monitored host during the flood, compared with the number sent.
  - Neighbor table size on the target host, before and after the flood.
  - Switch or router logs for ARP rate limits or neighbor table overflow, if available.
- **Impact**: degraded performance of every host on the segment, neighbor table exhaustion on the router (new hosts cannot be resolved), and loss of connectivity for hosts whose entries are evicted.
- **Mitigations**: ARP rate limiting and control-plane policing, bounded neighbor tables with eviction policies, port-based ARP rate limits on the switch, and ARP inspection.
- **Execution risk**: **Active Test**, with a limited number of requests. Flooding a production segment is **Destructive Lab** only.

### Implementation notes

- Each request has a random unicast sender MAC and a random sender IP from the subnet, and is sent to broadcast.
- The target is a fixed IP, for example the gateway, which makes the target answer every sender and fill its table. Without a fixed target the requests ask for random hosts of the subnet.
- With a fixed target and a /24 subnet, random senders repeat, so the neighbor table grows to roughly the number of distinct sender IPs, not to the request count.
- The attacker's own MAC is not used as sender: every request carries a random one. The attacker can only be identified by the interface it sends from.

### Lab validation

`scripts/lab/arp_request_flooding_lab.sh` uses a Linux bridge with a victim, the gateway and the attacker. The last run (200 requests for the gateway's IP):

- The victim received 200 of 200 flooded requests.
- The gateway's neighbor table went from 1 entry to 133. The subnet has 254 hosts, so repeated random senders account for the difference from 200.

## ARP Reply Flooding ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet, operation reply (2).
- **Technical reference**: RFC 826 (Address Resolution Protocol). Linux neighbor table behavior (which packets create or update entries). Vendor documentation on ARP rate limiting and control-plane policing.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the segment. The subnet to draw sender addresses from.
- **Compatibility**: any IPv4 segment. The effect on a host depends on how it treats unsolicited replies: every host parses each broadcast, but a host only changes the entries it already holds.
- **Expected behavior**:
  - Vulnerable: every host processes each broadcast reply, which costs CPU. A host that holds an entry for a claimed sender updates that entry, so its cache churns.
  - Protected: ARP rate limiting or control-plane policing, Dynamic ARP Inspection that drops replies whose sender is not in the binding table, and bounded neighbor tables.
- **Evidence**:
  - Replies received by a monitored host during the flood, compared with the number sent.
  - Neighbor table of the victim before and after the flood.
  - Switch or router logs for ARP rate limits or inspection drops, if available.
- **Impact**: processing load on every host on the segment, cache churn for hosts that track the claimed senders, and disruption for a host whose entry is replaced.
- **Mitigations**: ARP rate limiting and control-plane policing, Dynamic ARP Inspection, and monitoring of ARP reply rates per port.
- **Execution risk**: **Active Test**, with a limited number of replies. Flooding a production segment is **Destructive Lab** only.

### Implementation notes

- Each reply has a random unicast sender MAC and a random sender IP from the subnet, and is sent to broadcast.
- The victim IP is fixed, or a random host of the subnet when left empty. With a fixed victim, every reply is addressed to that host.
- Replies are unsolicited: the attacker needs no state on the victim.
- The attacker's own MAC is not used as sender. Each reply carries a random one.

### Lab validation

`scripts/lab/arp_reply_flooding_lab.sh` uses a Linux bridge with a victim, the gateway and the attacker. The last run (200 replies addressed to the victim's IP):

- The victim received 200 of 200 replies.
- The victim's neighbor table stayed at one entry (the gateway). Linux did not create entries for the random senders, because it updates only entries it already holds. In this run the effect is processing load on the victim. Cache churn needs a host that already holds entries for the claimed senders, which the lab does not create.

## ARP-Based Gateway Impersonation ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet, operation reply (2).
- **Technical reference**: RFC 826 (Address Resolution Protocol). Linux neighbor table behavior for unsolicited replies (`arp_locktime`, which replies update an existing entry). Linux IP forwarding (`net.ipv4.ip_forward`).
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the victims' segment, and the list of victim IPs. Changing IP forwarding needs root.
- **Compatibility**: any IPv4 segment whose hosts use a default gateway. The effect depends on whether the hosts accept unsolicited replies that update an entry they already hold.
- **Expected behavior**:
  - Vulnerable: each listed host caches the attacker's MAC for the gateway's IP and sends its off-subnet traffic there. If forwarding is off on the attacker, the traffic is dropped.
  - Protected: dynamic ARP inspection that drops replies for the gateway from an untrusted port, static gateway entries on critical hosts, and monitoring of the gateway's MAC address.
- **Evidence**:
  - The cached MAC for the gateway's IP on each victim, before and after the attack.
  - The attacker's IP forwarding setting during the attack, and after it is restored.
  - Switch logs for ARP inspection drops or MAC changes on the gateway's address, if available.
- **Impact**: interception of all off-subnet traffic of the victims, or, without forwarding, loss of their connectivity beyond the segment.
- **Mitigations**: dynamic ARP inspection with trusted ports for the gateway only, static ARP entries for the gateway on critical hosts, DHCP snooping bindings, and alerts when the gateway's MAC address changes.
- **Execution risk**: **Active Test**, on a short window with a limited set of victims. Interception of production gateway traffic is **Destructive Lab** only.

### Implementation notes

- Each round sends one reply per victim, each claiming the gateway's IP at the attacker's MAC, broadcast on the segment.
- The attacker's MAC is read with `ip`, not from Scapy, because Scapy caches the interface MAC when it loads.
- Forwarding is enabled before the first reply and restored in a `finally` block, so it is restored even if sending fails.
- Victims are a list of IPs, not the whole subnet. The gateway cannot be a victim.
- Unlike ARP spoofing, which binds an address to one victim, this attack is scoped to the gateway and changes the attacker's routing behavior.

### Lab validation

`scripts/lab/arp_gateway_impersonation_lab.sh` uses a Linux bridge with two victims, the gateway and the attacker. The last run (13 rounds, 26 replies, 3 seconds):

- Both victims' cached MAC for the gateway changed from the gateway's MAC to the attacker's MAC.
- Forwarding was 1 during the attack and 0 afterwards, the value it had before.
- The lab waits 3 seconds after the baseline. In a first run without the wait, the first victim kept the gateway's MAC: Linux ignored the unsolicited updates for an entry it had confirmed a moment before. The lab documents this and waits.
- The lab stops at the ARP caches and does not route traffic beyond the segment.

## Switch Spoofing / DTP Spoofing 🔨

**Family**: VLAN & IEEE 802.1Q. **Priority**: P1.

- **Protocol**: Dynamic Trunking Protocol (DTP, Cisco proprietary), SNAP-encapsulated in an 802.3 frame to the multicast address `01:00:0c:cc:cc:cc`, with protocol `0x2004`.
- **Technical reference**: Cisco DTP documentation (trunk negotiation modes, status and type values). Vendor documentation on disabling DTP on access ports.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the access port under test. No other requirements.
- **Compatibility**: switch ports that run DTP in a dynamic mode (`dynamic auto`, `dynamic desirable`) and accept the negotiation. Ports set to `switchport mode access` with DTP disabled do not negotiate.
- **Expected behavior**:
  - Vulnerable: a dynamic port accepts the trunk advertisement and becomes a trunk, so the host receives tagged frames for every allowed VLAN.
  - Protected: access mode with DTP disabled (`switchport nonegotiate` on trunks, `switchport mode access` on user ports), and alerts on trunk formation on access ports.
- **Evidence**:
  - DTP frames sent by the attacker, and frames seen on the port under test.
  - The port's mode and operational state before and after the advertisements, from the switch.
  - Tagged frames received on the host, if a trunk is formed.
- **Impact**: access to every VLAN allowed on the trunk, which breaks the separation that VLANs provide.
- **Mitigations**: access mode on user ports with DTP disabled, `nonegotiate` on every trunk, shut down unused ports, and monitoring of trunk formation.
- **Execution risk**: **Active Test**, on a port that is authorized for the test. Negotiating trunks on production ports is **Destructive Lab** only.

### Implementation notes

- Each frame carries a DTP body with the VTP domain (optional), a trunk-desirable status, the 802.1Q encapsulation type and the attacker's MAC as neighbor.
- The sender MAC is read with `ip`, not from Scapy, because Scapy caches the interface MAC when it loads.
- The length field is the 802.3 payload length. The payload layout follows the public DTP description and has not been checked against a capture from a real switch.

### Lab validation

`scripts/lab/switch_spoofing_lab.sh` uses a Linux bridge with the attacker and a monitor port. The last run (10 DTP frames):

- The monitor saw 10 of 10 frames, all with the DTP multicast address, the LLC/SNAP header and the attacker's source MAC. 0 were malformed.
- A Linux bridge does not run DTP and does not form trunks. The lab therefore does not test whether a switch negotiates a trunk. That needs a switch with DTP enabled, so the technique is marked as implemented, not tested.

## VLAN Hopping 🔨

**Family**: VLAN & IEEE 802.1Q. **Priority**: P1.

- **Protocol**: IEEE 802.1Q tagging (EtherType `0x8100`, VLAN ID in the tag). The optional first step uses DTP (Cisco proprietary, see switch spoofing).
- **Technical reference**: IEEE 802.1Q-2018 (VLAN tag and membership). Cisco DTP documentation for the negotiation. Vendor documentation on access port behavior with tagged frames.
- **Requirements**: root or `CAP_NET_RAW` on the access port under test, and a target VLAN the port should not reach. A monitor on the target VLAN, or a host that can see the reply, to confirm the result.
- **Compatibility**: access ports that accept or forward tagged frames, and ports that negotiate into a trunk through DTP. Ports that drop tagged frames on access and have DTP disabled are not affected.
- **Expected behavior**:
  - Vulnerable: tagged frames for a VLAN the port does not belong to reach that VLAN, either because the port became a trunk or because it accepts tags on access.
  - Protected: access ports that drop tagged frames, DTP disabled on user ports, and no trunk on ports that connect to hosts.
- **Evidence**:
  - Probes sent by the attacker, with their VLAN tag.
  - Probes seen on the target VLAN by a monitor, before and after the port carries the VLAN.
  - The port's mode and VLAN membership from the switch, if available.
- **Impact**: access to the hosts and services of a VLAN that the port should be isolated from.
- **Mitigations**: access ports that drop tagged frames, DTP disabled on user ports, a dedicated native VLAN that carries no user traffic, and alerts on frames tagged for unexpected VLANs.
- **Execution risk**: **Active Test** on an authorized port, with a probe that carries no payload. Reaching production VLANs is **Destructive Lab** only.

### Implementation notes

- The optional first frame is the DTP advertisement from switch spoofing, sent once.
- Each probe is an ARP request from the zero address (`psrc 0.0.0.0`) for the probe IP, tagged with the target VLAN. It carries no data, and the address is in the documentation range by default.
- The sender MAC is read with `ip`, not from Scapy, because Scapy caches the interface MAC when it loads.

### Lab validation

`scripts/lab/vlan_hopping_lab.sh` uses a Linux bridge with the attacker and a monitor port. The port's VLAN membership is emulated with an nftables bridge rule, because the lab kernel has no VLAN-filtering bridges. The last run (10 probes tagged with VLAN 20):

- Phase 1, access port: 0 of 10 probes reached the monitor.
- Phase 2, port carries VLAN 20 tagged: 10 of 10 probes reached the monitor.
- The phase 2 rule is a simulated trunk outcome. The lab does not show that DTP creates it, so the technique is marked as implemented, not tested.

## Double-Tagging 🔨

**Family**: VLAN & IEEE 802.1Q. **Priority**: P1.

- **Protocol**: IEEE 802.1Q tagging with two tags (outer and inner, both EtherType `0x8100`).
- **Technical reference**: IEEE 802.1Q-2018 (native VLAN, tag handling on trunks). Vendor documentation on native VLAN handling.
- **Requirements**: root or `CAP_NET_RAW` on the access port under test, a native VLAN of the trunk that matches the outer tag, and a target VLAN that the port should not reach. A monitor on the target VLAN confirms the result.
- **Compatibility**: a trunk whose native VLAN equals the outer tag, where the switch removes the outer tag before forwarding. Switches that drop frames with more than one tag, or that do not strip the native VLAN, are not affected.
- **Expected behavior**:
  - Vulnerable: the switch removes the outer tag on the native VLAN and forwards the frame into the inner VLAN. The traffic is one way.
  - Protected: the native VLAN is unused for user traffic, native VLAN traffic is tagged on trunks, and frames with more than one tag are dropped on access ports.
- **Evidence**:
  - Frames sent with both tags, as seen on the attacker's port.
  - Frames seen on the target VLAN by a monitor, and whether the outer tag is still present.
  - Switch counters for dropped or stripped tags, if available.
- **Impact**: access to the hosts and services of a VLAN the port should be isolated from, without any negotiation, and for traffic in one direction only.
- **Mitigations**: a native VLAN that carries no user traffic, tagging of the native VLAN on trunks, dropping of frames with more than one tag on access ports, and monitoring of frames tagged for unexpected VLANs.
- **Execution risk**: **Active Test** on an authorized port, with a probe that carries no payload. Reaching production VLANs is **Destructive Lab** only.

### Implementation notes

- Each frame has the native VLAN as outer tag and the target VLAN as inner tag. The native and target VLANs must differ.
- The payload is an ARP probe from the zero address, as in VLAN hopping. It carries no data.
- The sender MAC is read with `ip`, not from Scapy, because Scapy caches the interface MAC when it loads.

### Lab validation

## Native VLAN Abuse 🔨

**Family**: VLAN & IEEE 802.1Q. **Priority**: P1.

- **Protocol**: IEEE 802.1Q trunking. Frames of the native VLAN travel untagged, and the two ends of the trunk must agree on which VLAN is native.
- **Technical reference**: IEEE 802.1Q-2018 (native VLAN, untagged frames on trunks). Vendor documentation on native VLAN configuration and on tagging the native VLAN.
- **Requirements**: root or `CAP_NET_RAW` on a port in the native VLAN of its trunk, and a far end whose native VLAN differs. A monitor in the far end's native VLAN confirms where the frames land.
- **Compatibility**: trunks whose two ends use different native VLANs, or whose native VLAN carries user traffic. Trunks with matching native VLANs, or with native VLAN tagging enabled, are not affected.
- **Expected behavior**:
  - Vulnerable: untagged frames sent on the native VLAN of one end arrive in the native VLAN of the other end, which can be a VLAN the sender does not belong to.
  - Protected: identical native VLANs on both ends, an unused native VLAN, and native VLAN tagging on trunks.
- **Evidence**:
  - Untagged probes sent by the attacker.
  - The VLAN in which the probes arrive at a monitor on the far end.
  - The native VLAN configuration of both ends of each trunk, from the switches.
- **Impact**: traffic that crosses into another VLAN without a tag, in one direction. Hosts in the far end's native VLAN can be reached from a port that belongs to another VLAN.
- **Mitigations**: identical native VLAN on both ends of every trunk, a native VLAN that carries no user traffic, tagging of native VLAN traffic on trunks, and alerts on native VLAN mismatches.
- **Execution risk**: **Active Test**, with a limited number of probes, on a trunk that is authorized for the test. Sending into production VLANs is **Destructive Lab** only.

### Implementation notes

- Each probe is an untagged ARP request from the zero address for the probe IP. It carries no data.
- The attack needs no configuration of the native VLAN: the VLAN is a property of the far end's trunk. The attacker only sends untagged frames.
- The sender MAC is read with `ip`, not from Scapy, because Scapy caches the interface MAC when it loads.

### Lab validation

`scripts/lab/native_vlan_lab.sh` uses a Linux bridge with the attacker and a monitor port. The last run (10 untagged probes):

- The monitor received 10 of 10 probes, all untagged.
- The mismatch itself is not tested. The lab kernel has no VLAN-filtering bridges and no VLAN push action, so it cannot place untagged frames into another VLAN. The test needs two real switches with different native VLANs on the two ends of a trunk. The technique is marked as implemented, not tested.

## VLAN Tag Injection 🔨

**Family**: VLAN & IEEE 802.1Q. **Priority**: P1.

- **Protocol**: IEEE 802.1Q tag (EtherType `0x8100`, with the tag control information: priority code point PCP, drop eligible indicator DEI and VLAN ID).
- **Technical reference**: IEEE 802.1Q-2018 (tag format, priority regeneration, DEI). Vendor documentation on tag handling on access ports.

- **Compatibility**: access ports that accept tagged frames, or that keep or rewrite the PCP and DEI fields. Access ports that drop tagged frames are not affected.
- **Expected behavior**:
  - Vulnerable: the switch accepts a tag on an access port, places the frame in the VLAN the tag names, and keeps the chosen priority, which can change quality of service on the path.

- **Impact**: access to a VLAN the port should not reach, and manipulation of the priority of traffic on the path.
- **Mitigations**: access ports that drop tagged frames, priorities assigned by the switch from the port, and alerts on tagged frames arriving on access ports.
- **Execution risk**: **Active Test** on an authorized port, with a probe that carries no payload. Injecting into production VLANs is **Destructive Lab** only.

- Each probe is an ARP request from the zero address for the probe IP, carrying a tag with the chosen VLAN ID, PCP and DEI.

## BPDU Spoofing ✅

**Family**: Spanning Tree (STP / RSTP / MSTP / PVST+). **Priority**: P1.

- **Protocol**: IEEE 802.1D configuration BPDU, sent to `01:80:c2:00:00:00` with an LLC header (`42 42 03`). It carries the root identifier, root path cost, bridge identifier, port identifier and timers.
- **Technical reference**: IEEE 802.1D-2004 (BPDU format and root election). IEEE 802.1w for RSTP.
- **Requirements**: root or `CAP_NET_RAW` on the switch port under test, and an authorized test network. The root port and topology of the switch must be observable, for example through its CLI or logs.
- **Compatibility**: switches that run STP on the port, which is the default on most switches. Ports with BPDU Guard or BPDU filter discard the frames.
- **Expected behavior**:
  - Vulnerable: the switch accepts a superior root from the port, moves its root port to that port, and recalculates the tree.
  - Protected: BPDU Guard shuts the port down, or the switch keeps its root port on the legitimate path because the port's information is not superior.
- **Evidence**:
  - BPDUs sent, with root ID, bridge ID and timers.
  - The switch's root port before, during and after the injection.
  - The time the switch takes to return to the legitimate root after the BPDUs stop.
- **Impact**: change of the root bridge, traffic redirected through the attacker's port, and a possible loop or outage during convergence.
- **Mitigations**: BPDU Guard on access ports, Root Guard on ports where the root must not move, an explicit root priority on the intended root bridge, and logging of root changes.
- **Execution risk**: **Active Test** on an authorized port, with a test topology. Changing the root of a production network is **Destructive Lab** only.

### Implementation notes

- The configuration BPDU follows the 802.1D layout: 35 bytes after the LLC header. Timers are in units of 1/256 second. The injected BPDUs use a max age of 20 s, a hello time of 2 s and a forward delay of 15 s.
- The root priority must be a multiple of 4096 between 0 and 61440, and lower values win. The root MAC defaults to the sender, so a bridge can claim to be the root from its own MAC.
- The sender MAC is read with `ip`, not from Scapy, because Scapy caches the interface MAC when it loads.

### Lab validation

`scripts/lab/bpdu_spoofing_lab.sh` runs the Linux kernel's 802.1D Spanning Tree on the switch bridge. A legitimate root bridge (priority 8192) is on one switch port, and the attacker is on the other, advertising priority 0. The last run (10 BPDUs, 0.5 s apart):

- Baseline: the switch's root port is the port toward the legitimate root.
- Attack: the switch moves its root port to the attacker's port.
- Recovery: after the BPDUs stop, the injected information expires after its 20 s max age, and the root port returns to the legitimate root.

The lab reads the root port, because on the lab kernel the designated root that `ip -d link` prints does not follow the election. Vendor behavior, such as BPDU Guard and Root Guard, is not tested here.

## Root Bridge Takeover ✅

**Family**: Spanning Tree (STP / RSTP / MSTP / PVST+). **Priority**: P1.

- **Protocol**: IEEE 802.1D configuration BPDUs in which the root identifier equals the sender's bridge identifier, refreshed at the hello interval.
- **Technical reference**: IEEE 802.1D-2004 (root election by bridge ID, and the max age that keeps the stored root information). IEEE 802.1w and 802.1s for the rapid and multiple-instance variants.
- **Requirements**: root or `CAP_NET_RAW` on the switch port under test, and an authorized test network. The root port or the root bridge of the switch must be observable.
- **Compatibility**: switches that run STP on the port. Ports with Root Guard or BPDU Guard do not accept a superior root, so the claim does not take effect.
- **Expected behavior**:
  - Vulnerable: the switch accepts the claim, keeps its root port toward the attacker while the claim is refreshed, and sends its traffic along the attacker's paths.
  - Protected: Root Guard blocks the port, or the switch keeps the legitimate root because the claim is not superior.
- **Evidence**:
  - Claims sent, with the claimed priority and bridge ID, and their interval.
  - The switch's root port at intervals during the claim, including after the first claim's max age has passed.
  - The time the switch takes to return to the legitimate root after the claim stops.
- **Impact**: the attacker's bridge becomes the center of the forwarding paths, so traffic can cross links it should not, and the topology is rebuilt for as long as the claim is kept.
- **Mitigations**: Root Guard on access and distribution ports, fixed priorities on core switches, and alerts on root changes.
- **Execution risk**: **Active Test** on an authorized port, on a test topology. Taking the root of a production network is **Destructive Lab** only.

### Implementation notes

- The claim is a configuration BPDU whose root and bridge identifiers are both the sender's MAC at the claimed priority. Refreshed at the 2 s hello interval, it keeps the stored root information alive on the switch. [BPDU spoofing](bpdu-spoofing.md) sends the same frames, but for a single advertisement.
- The claimed priority must be a multiple of 4096 between 0 and 61440. The module does not listen for a rival root, so it does not back off when a better one appears.
- The sender MAC is read with `ip`, not from Scapy.

### Lab validation

`scripts/lab/root_bridge_takeover_lab.sh` runs the Linux kernel's 802.1D Spanning Tree on the switch. A legitimate root bridge (priority 8192) is on one port, and the attacker claims priority 0 on the other, refreshing the claim for about 28 s. The last run:

- Baseline: the switch's root port is the port toward the legitimate root.
- Takeover: the root port is on the attacker's port at 4, 14 and 26 s. The 26 s sample is past the first claim's 20 s max age, so the takeover depends on the refreshes.
- Recovery: after the claim stops, the root port returns to the legitimate root.

The lab reads the root port, because on the lab kernel the designated root that `ip -d link` prints does not follow the election. Vendor behavior, such as Root Guard, is not tested here.

## Root Bridge Impersonation ✅

**Family**: Spanning Tree (STP / RSTP / MSTP / PVST+). **Priority**: P1.

- **Protocol**: IEEE 802.1D configuration BPDUs whose root identifier is copied from the real root, sent from a different bridge identifier and port.
- **Technical reference**: IEEE 802.1D-2004 (root identifier, root path cost, and the rules that choose the root port by cost, then sender bridge ID, then port ID).
- **Requirements**: root or `CAP_NET_RAW` on the switch port under test, and an authorized test network. The root identifier of the real root must be read from its BPDUs, which the attacker can do passively on the same segment.
- **Compatibility**: switches that run STP on the port. Root Guard and BPDU Guard on the port stop the impostor's advertisements.
- **Expected behavior**:
  - Vulnerable: the switch keeps the impostor's port as its root port while the impostor is refreshed, and the root identifier looks unchanged in the switch's output.
  - Protected: the switch detects a second bridge with the root identifier on another port, or it keeps its path on the real root's port.
- **Evidence**:
  - BPDUs sent, with the copied root identifier, the attacker's bridge identifier and the advertised root path cost.
  - The switch's root port at intervals during the impersonation.
  - The time the switch takes to return to the real root after the impersonation stops.
- **Impact**: traffic that follows the tree is redirected through the impostor's port, and monitoring that checks only the root identifier does not notice the change.
- **Mitigations**: Root Guard, monitoring of root port changes and of advertisements from unexpected ports, and BPDU Guard on access ports.
- **Execution risk**: **Active Test** on an authorized port, on a test topology. Impersonating the root of a production network is **Destructive Lab** only.

### Implementation notes

- The module refuses a root MAC that equals the interface's own MAC, because that is a takeover (see [root bridge takeover](root-bridge-takeover.md)), not an impersonation.
- The attacker advertises a root path cost of 0 and bridge priority 0. The real root also advertises cost 0, so the switch compares the sending bridge IDs, and the impostor's lower ID wins the tie.
- The root priority and MAC are required inputs, copied from the real root's BPDUs. The sender MAC is read with `ip`, not from Scapy.

### Lab validation

`scripts/lab/root_bridge_impersonation_lab.sh` runs the Linux kernel's 802.1D Spanning Tree on the switch. The real root (priority 8192) is on one port, and the attacker sends the real root's ID from the other port, with its own bridge priority 0 and cost 0. The last run (15 BPDUs, 2 s apart):

- Baseline: the switch's root port is the port toward the real root.
- Impersonation: the root port is on the attacker's port at 4, 14 and 26 s, while the impostor is refreshed.
- Recovery: after the impersonation stops, the root port returns to the real root.

The lab reads the root port, because on the lab kernel the designated root that `ip -d link` prints does not follow the election. The lab does not test a switch that detects the duplicate root identifier, such as one with Root Guard.

## Topology Change Flooding 🔨

**Family**: Spanning Tree (STP / RSTP / MSTP / PVST+). **Priority**: P1.

- **Protocol**: IEEE 802.1D configuration BPDUs with the topology change (TC) flag set, honored on the root port.
- **Technical reference**: IEEE 802.1D-2004 (topology change notification and the flush of learned addresses on a topology change).
- **Requirements**: root or `CAP_NET_RAW` on the switch port under test, and an authorized test network. The attacker must win the root port for the flag to count, so it advertises the real root's ID, as in [root bridge impersonation](root-bridge-impersonation.md).
- **Compatibility**: switches that run STP on the port and that act on the TC flag from their root port.
- **Expected behavior**:
  - Vulnerable: the switch shortens its address ageing and flushes learned addresses while the flag keeps arriving, so frames flood until the addresses are learned again.
  - Protected: the switch ignores the flag from a port that is not its designated or root path, or it limits how often a topology change can flush its table.
- **Evidence**:
  - BPDUs sent with the TC flag set, and the root ID they carry.
  - The switch's table entry for a host that stopped sending, with and without the flag.
  - A control run of the same root stream without the flag, to attribute any flush to the flag.
- **Impact**: repeated flushing of the MAC table, which floods unicast traffic until addresses are relearned, and exposes that traffic to a device on the path.
- **Mitigations**: BPDU Guard on access ports, Root Guard, and rate limits or protection against topology change notifications on the switch.
- **Execution risk**: **Active Test** on an authorized port, on a test topology. Flushing the tables of a production network is **Destructive Lab** only.

### Implementation notes

- The TC flag is bit 0 of the BPDU flags byte. The BPDU builder takes a `flags` argument, and the default is 0, so the other attacks are unchanged.
- The module reuses the root-ID sender of root bridge impersonation, with the flag set, and it applies the same checks.

### Lab validation

`scripts/lab/topology_change_flooding_lab.sh` has a control run and a flood run of equal length, from the same attacker and root ID. The last run:

- Baseline: the monitor's MAC is learned, and the root port is the real root's.
- Control, no TC flag: the root port moves to the attacker, and the monitor's MAC stays learned. The kernel sets its topology change detected flag once, from the root change.
- Flood, TC flag set: the root port moves to the attacker, the monitor's MAC stays learned, and the detected flag does not change.

The effect is not reproduced on this lab kernel: it does not flush its table on the TC flag from the root port. The BPDUs are sent and received correctly, so the attack is implemented, not tested. The result needs a switch that acts on the flag to be confirmed.

## TCN Spoofing 🔨

**Family**: Spanning Tree (STP / RSTP / MSTP / PVST+). **Priority**: P1.

- **Protocol**: IEEE 802.1D topology change notification (TCN) BPDU, a four-byte BPDU of type `0x80` sent toward the root. The designated bridge acknowledges it with the TCA flag and propagates the topology change.
- **Technical reference**: IEEE 802.1D-2004 (TCN and TCA, and the topology change procedure).
- **Requirements**: root or `CAP_NET_RAW` on a switch port that is designated, for example a port with a single host behind it, and an authorized test network.
- **Compatibility**: switches that run STP on the port. Ports with BPDU Guard or BPDU filter discard the TCNs.
- **Expected behavior**:
  - Vulnerable: the switch accepts the TCNs, acknowledges them, and flushes the learned addresses for the affected ports.
  - Protected: the switch ignores TCNs from the port, or it limits how often a topology change can flush its table.
- **Evidence**:
  - TCNs sent.
  - TCA acknowledgments received by the attacker.
  - The switch's topology change detected state during the flood, and the learned address of a host that stopped sending, with a control run of equal length without TCNs.
- **Impact**: repeated MAC table flushes, which flood unicast traffic until addresses are relearned.
- **Mitigations**: BPDU Guard on access ports, and limits on or protection against topology change notifications on the switch.
- **Execution risk**: **Active Test** on an authorized port, on a test topology. Flushing the tables of a production network is **Destructive Lab** only.

### Implementation notes

- The TCN has no configurable fields. The sender MAC is read with `ip`, not from Scapy.
- The attack does not need to win the root port. It works from a designated port, unlike [topology change flooding](topology-change-flooding.md).

### Lab validation

`scripts/lab/tcn_spoofing_lab.sh` puts the attacker on a designated port of the switch, with the real root unchanged on the other port. Thirty TCNs were sent over 15 s, with a control of equal length without TCNs. The last run:

- Control: the monitor's MAC stayed learned, and the topology change flag stayed 0.
- Acknowledged: the switch sent 16 TCA acknowledgments to the attacker, so it accepted the TCNs.
- Topology change: the flag rose to 1 at 8 s and fell back by 14 s, which matches the kernel's topology change timer.
- Flush: the monitor's MAC was not flushed during the flood.

This is a partial reproduction. The switch acts on TCNs, but the table flush that defines the impact is not observed on this lab kernel. The result needs a real switch to confirm the flush, so the attack is implemented, not tested.

## BPDU Flooding 🔨

**Family**: Spanning Tree (STP / RSTP / MSTP / PVST+). **Priority**: P1.

- **Protocol**: IEEE 802.1D configuration BPDUs, sent at a high rate from many source MACs and bridge identities.
- **Technical reference**: IEEE 802.1D-2004 (BPDU processing and the timers of the spanning tree).
- **Requirements**: root or `CAP_NET_RAW` on a switch port under test, and an authorized test network. Flood rates must stay within what the test network can absorb.
- **Compatibility**: switches that run STP on the port. Ports with BPDU Guard shut down on the first BPDU, and rate limits on the control plane reduce the effect.
- **Expected behavior**:
  - Vulnerable: the switch's control-plane load rises, and real spanning-tree updates are delayed. Convergence after a real change takes longer during the flood.
  - Protected: the switch rate-limits or drops excess BPDUs, or the flood does not delay real updates.
- **Evidence**:
  - BPDUs sent, with the rate.
  - Frames received by the switch on the port under test, against the expected count.
  - Whether the topology changed during the flood, and the time real spanning-tree updates take to converge with and without the flood.
- **Impact**: slower spanning-tree convergence after a real failure, and a load on the switch's control plane.
- **Mitigations**: BPDU Guard on access ports, control-plane policing of BPDUs, and rate limits on STP traffic.
- **Execution risk**: **Active Test** at a low rate on an authorized port. A high rate on a production switch is **Destructive Lab** only.

### Implementation notes

- Each frame has a random locally administered source MAC and a random root ID at priority 61440. None of them can win the election, so the topology should not change.
- The rate is limited to 5000 BPDUs per second. The module sends in batches of 0.1 s.

### Lab validation

`scripts/lab/bpdu_flooding_lab.sh` floods the switch from an access port at 500 BPDUs per second for 10 s. The last run:

- Control: no frames arrived on the attacker's port with no flood.
- Delivery: the switch received 5000 of 5000 flooded BPDUs.
- Topology: the root port stayed on the real root, and the monitor's MAC stayed learned.

The lab does not measure the switch's control-plane load, or how much a flood delays real spanning-tree updates. That needs a second legitimate path and a timed convergence event, so the attack is implemented, not tested.

## Rogue DHCP Server ✅

**Family**: DHCPv4 & DHCPv6. **Priority**: P1.

- **Protocol**: DHCPv4 (RFC 2131 message exchange, RFC 2132 options). The rogue answers DISCOVER with OFFER, carrying its own server identifier, router and DNS options, and answers REQUEST with ACK when it is the named server.
- **Technical reference**: RFC 2131 (client selection of an offer, and the server identifier), RFC 2132 (router and DNS options).
- **Requirements**: root or `CAP_NET_RAW` on a host on the same segment as the clients, and an authorized test network.
- **Compatibility**: DHCPv4 clients that take the first offer, which is the common behavior. Clients that wait for several offers, or DHCP snooping on the switch, reduce the effect.
- **Expected behavior**:
  - Vulnerable: clients accept the rogue's offer and ACK, and configure the rogue as gateway and DNS server.
  - Protected: DHCP snooping drops the rogue's offers from untrusted ports, or the legitimate server's offer arrives first and the client chooses it.
- **Evidence**:
  - Offers and ACKs sent by the rogue.
  - Per client round, which server's offer arrived first, the router and address it carried, and which server ACKed the lease.
  - The same rounds with the legitimate server running and stopped.
- **Impact**: clients route their traffic through the attacker, and their DNS queries go to the attacker. This is a man-in-the-middle position.
- **Mitigations**: DHCP snooping with trusted ports, Dynamic ARP Inspection, and alerts on offers from unexpected servers.
- **Execution risk**: **Active Test** on an authorized segment, with a test client. Taking over DHCP for a production network is **Destructive Lab** only.

### Implementation notes

- The responder is a set of pure functions (`respond`, `build_offer`, `build_ack`), plus a sniffer that calls them. The tests drive the functions directly.
- A REQUEST is answered only when it names this server, so the rogue does not interfere with exchanges that chose another server.

### Lab validation

`scripts/lab/rogue_dhcp_server_lab.sh` puts dnsmasq, the rogue and a client on one bridge. Each round is a full DISCOVER, OFFER, REQUEST and ACK. The last run (5 rounds per phase):

- Baseline: every first offer came from the legitimate server.
- Race: with both servers running, the first offer came from the rogue in 0 of 5 rounds. The legitimate server answered first in this lab.
- Alone: with the legitimate server stopped, the client took the rogue's offer in 5 of 5 rounds, configured with the rogue's gateway and DNS, and the rogue ACKed the lease in 5 of 5.

The attack works when the legitimate server is slow, down or out of addresses. It did not win the race against dnsmasq on this host, so the lab does not show that a rogue beats a responsive server. Confirming that needs a more responsive setup, which the lab does not provide.

## DHCP Spoofing ✅

**Family**: DHCPv4 & DHCPv6. **Priority**: P1.

- **Protocol**: DHCPv4 (RFC 2131 message exchange, RFC 2132 options). The spoofer answers DISCOVER with OFFER and REQUEST with ACK, using the legitimate server's IP address as source and server identifier, and its MAC address as the frame source.
- **Technical reference**: RFC 2131 (server identifier and the client's choice of offer), RFC 2132 (router and DNS options).
- **Requirements**: root or `CAP_NET_RAW` on a host on the segment, the legitimate server's address and MAC (both visible in its traffic), and an authorized test network.
- **Compatibility**: DHCPv4 clients that take the first offer. DHCP snooping that checks the server's port, and clients that wait for several offers, reduce the effect.
- **Expected behavior**:
  - Vulnerable: the client accepts the spoofed offer and ACK as coming from the legitimate server, and configures the spoofed gateway and DNS server.
  - Protected: DHCP snooping on the server's port drops the spoofed offers, or the legitimate server's offer arrives first and the client chooses it.
- **Evidence**:
  - Offers and ACKs sent, with the server identity they carry.
  - Per client round, which offer arrived first, its gateway, and which server identity acknowledged the lease.
  - The same rounds with the legitimate server running and stopped.
- **Impact**: the client routes its traffic through the attacker, and it cannot tell from the server identity that the configuration changed.
- **Mitigations**: DHCP snooping with trusted ports on the server's port, Dynamic ARP Inspection, and alerts when a server identity offers different values.
- **Execution risk**: **Active Test** on an authorized segment with a test client. Impersonating the DHCP server of a production network is **Destructive Lab** only.

### Implementation notes

- The module reuses the rogue server's responder. The only differences are the identity it sends (the legitimate server's IP and MAC) and an optional target client MAC, so the other clients keep the real server.
- The legitimate server's MAC is required, because the attack has to copy it.

### Lab validation

`scripts/lab/dhcp_spoofing_lab.sh` puts dnsmasq, the spoofer and a client on one bridge. The spoofer copies dnsmasq's MAC and address, and it answers only the client's MAC. The last run (5 rounds per phase):

- Baseline: every first offer named the legitimate gateway.
- Race: with both servers running, the first offer carried the spoofed gateway in 0 of 5 rounds. The legitimate server answered first in this lab.
- Alone: with the legitimate server stopped, the client took the spoofed offer in 5 of 5 rounds, and it was acknowledged as `10.99.0.1`, with the spoofed gateway, in 5 of 5.

The attack works when the legitimate server is slow, down or out of addresses. The lab does not show that a spoofer beats a responsive server, and it does not test DHCP snooping.

## DHCP Offer Flooding ✅

**Family**: DHCPv4 & DHCPv6. **Priority**: P1.

- **Protocol**: DHCPv4 (RFC 2131). The flood answers each client DISCOVER with several OFFER messages, each from an invented server with its own identity, address and gateway.
- **Technical reference**: RFC 2131 (the client collects offers that match its transaction ID and chooses one), RFC 2132 (options carried by the offers).
- **Requirements**: root or `CAP_NET_RAW` on a host on the segment, so it can see the client's DISCOVER and match its transaction ID, and an authorized test network.
- **Compatibility**: clients that accept the first matching offer, or that process every offer. DHCP snooping that drops offers from untrusted ports reduces the effect.
- **Expected behavior**:
  - Vulnerable: the client receives the burst, and its first offer, or the one it chooses, comes from an invented server. Or the client spends its processing on the burst.
  - Protected: DHCP snooping drops the offers, or the legitimate server's offer arrives first and the client chooses it, and the burst is rate-limited.
- **Evidence**:
  - DISCOVERs answered and offers sent.
  - Per client round, the offers received, how many came from the flood, and which server sent the first one.
  - The same rounds with the legitimate server running and stopped.
- **Impact**: the client may take an address and gateway from a server that does not exist, or spend its processing on the burst.
- **Mitigations**: DHCP snooping with trusted ports, rate limits on DHCP offers, and client-side checks of offers against known servers.
- **Execution risk**: **Active Test** on an authorized segment with a test client. Flooding the DHCP service of a production network is **Destructive Lab** only.

### Implementation notes

- The offers are built from a random server MAC and identity per offer, with the client's transaction ID and client MAC, so the client treats each one as an answer to its DISCOVER.
- The invented servers and addresses are drawn from a network the operator chooses. The lab uses a range outside the legitimate pool.
- The burst is limited to 50 offers per DISCOVER.

### Lab validation

`scripts/lab/dhcp_offer_flooding_lab.sh` puts dnsmasq, the flood and a client on one bridge. The client sends DISCOVERs and records each offer that matches its transaction ID. The last run (5 rounds per phase):

- Baseline: one offer per round, all from the legitimate server.
- Race: with both running, each round received 11 offers, 10 of them from the flood, and the legitimate server's offer arrived first in every round.
- Alone: with the legitimate server stopped, the flood delivered 50 offers, and the client's first offer came from an invented server in 5 of 5 rounds.

The lab measures the choice effect. It does not measure the client's processing cost for the burst, which is the other goal in the theory, so that part is not tested. The client in the lab sends DISCOVERs only, so it does not confirm the lease.

## DHCP Discover Flooding 🔨

**Family**: DHCPv4 & DHCPv6. **Priority**: P1.

- **Protocol**: DHCPv4 (RFC 2131). DHCPDISCOVER messages from random client MACs, each with a random transaction ID, sent without any following REQUEST.
- **Technical reference**: RFC 2131 (the server's handling of a DISCOVER, and its offer state).
- **Requirements**: root or `CAP_NET_RAW` on a host on the server's segment, and an authorized test network. Flood rates must stay within what the test network can absorb.
- **Compatibility**: DHCP servers that answer DISCOVERs. Rate limits on DHCP at the switch (DHCP snooping rate limiting) reduce the effect.
- **Expected behavior**:
  - Vulnerable: the server's processing grows with the rate, its logs fill, and legitimate clients wait longer or get no offer.
  - Protected: the server or the switch rate-limits DISCOVERs, and legitimate clients keep getting offers.
- **Evidence**:
  - DISCOVERs sent, with the rate.
  - DISCOVERs logged by the server, against the number sent.
  - A probe client's offers before, during and after the flood.
- **Impact**: slower or lost service for legitimate clients, and a load on the server and its logs.
- **Mitigations**: DHCP snooping with rate limits on untrusted ports, and server-side rate limiting of DISCOVERs.
- **Execution risk**: **Active Test** at a low rate on an authorized segment. Flooding the DHCP service of a production network is **Destructive Lab** only.

### Implementation notes

- Each DISCOVER has a random locally administered client MAC and a random transaction ID. The module reuses the DISCOVER builder from DHCP starvation.
- The rate is limited to 5000 DISCOVERs per second, sent in batches of 0.1 s.

### Lab validation

`scripts/lab/dhcp_discover_flooding_lab.sh` floods dnsmasq from one port, with a probe client on another. The last runs:

- At 200 DISCOVERs per second for 10 s: the server logged 2002 of about 2000, and the probe received an offer before, during and after the flood.
- At 2000 DISCOVERs per second for 10 s: the server logged 20002 of about 20000, and the probe still received an offer during and after the flood.

The lab shows delivery at both rates, and no denial of service on dnsmasq. It does not measure the server's CPU use, and it does not show the degradation a slower server or a real switch would show. The attack is implemented, not tested.

## DHCP NAK Injection ✅

**Family**: DHCPv4 & DHCPv6. **Priority**: P1.

- **Protocol**: DHCPv4 (RFC 2131, DHCPNAK). A client renews its lease with a DHCPREQUEST sent to the server that granted it. The server answers with a DHCPACK, or with a DHCPNAK when it refuses the renewal. A client that receives a DHCPNAK stops using its address and starts again from DHCPDISCOVER.
- **Technical reference**: RFC 2131, section 4.3.2 (a DHCPNAK ends the client's use of its configuration).
- **Requirements**: root or `CAP_NET_RAW` on a host on the clients' segment, the legitimate server's address and MAC (copied from its traffic), and an authorized test network.
- **Compatibility**: DHCP clients that accept a NAK without checking its source. Clients that check the server identifier, or a switch that drops server messages from untrusted ports (DHCP snooping), are not affected.
- **Expected behavior**:
  - Vulnerable: a renewal is refused with a NAK in the server's name, and the client drops its lease and restarts.
  - Protected: DHCP snooping drops the forged NAK, or the client ignores it, and the renewal is acknowledged by the server.
- **Evidence**:
  - The client's renewal answered with ACK or NAK, and from which server, for each round.
  - The NAKs sent by the injector, and the requests it saw.
- **Impact**: clients drop their configuration and restart, so they lose connectivity for the time it takes to get a new lease.
- **Mitigations**: DHCP snooping, so server messages are accepted only from trusted ports. Monitoring of NAK rates. Clients that verify the server identifier before accepting a NAK.
- **Execution risk**: **Active Test** on an authorized segment, for one client with the target MAC option. Refusing every client on a production network is **Destructive Lab** only.

### Implementation notes

- Each NAK copies the request's transaction ID and client MAC, uses the legitimate server's address and MAC, and is sent to the broadcast address, as RFC 2131 suggests for a NAK.
- A REQUEST with a server identifier is answered only when the identifier matches the server. A renewal (no identifier, unicast to the server) and a reboot request (broadcast, no identifier) are answered too.
- Only REQUEST messages are answered. Replies from the server and frames sent by the injector itself are ignored.

### Lab validation

`scripts/lab/dhcp_nak_injection_lab.sh` runs dnsmasq as the legitimate server, with a client that takes a lease once and then renews it five times. The injector is limited to that client's MAC. The last run:

- Baseline, legitimate server only: all 5 renewals acknowledged by 10.99.0.1.
- Race, both servers running: the injector sent 5 NAKs, and the client still received an ACK first in all 5 rounds. In this lab the legitimate server answers first.
- Alone, legitimate server stopped: all 5 renewals refused with a NAK from 10.99.0.1. Vulnerable.

The alone phase is the reproduced impact. The race result shows that a NAK does not win against the legitimate server's ACK on this host, so a real attack depends on timing, or on a server that is slow, overloaded or unreachable.

## CDP Spoofing ✅

**Family**: Discovery & Management Protocols. **Priority**: P1.

- **Protocol**: Cisco Discovery Protocol, version 2. Advertisements go to the CDP multicast address `01:00:0c:cc:cc:cc`, in LLC/SNAP with the Cisco OUI and PID 0x2000. The message carries a TTL and a checksum over the whole message, then type-length-value fields: device ID, addresses, port ID, capabilities, software version, platform and native VLAN.
- **Technical reference**: Cisco CDP, as documented by Cisco for version 2 and as implemented by open-source receivers such as lldpd.
- **Requirements**: root or `CAP_NET_RAW` on a host on the segment with the receiver, and an authorized test network.
- **Compatibility**: receivers that keep CDP neighbors and act on them. Most switches and phones keep CDP enabled by default.
- **Expected behavior**:
  - Vulnerable: the receiver stores the forged neighbor, with its name, port, management address and native VLAN.
  - Protected: CDP is disabled on the access ports where it is not needed, or the receiver does not use CDP neighbors for any decision.
- **Evidence**:
  - The neighbor table before and after the advertisements.
  - The name, port, address and VLAN the receiver stored, against the advertised values.
  - The same advertisements with CDP disabled on the receiver.
- **Impact**: a false device appears in the neighbor inventory. Phones and tools that take settings from CDP may act on a forged native VLAN or address.
- **Mitigations**: disable CDP on untrusted and access ports, where it is not used. Do not treat CDP neighbors as an inventory. Use LLDP-MED or a secure voice configuration for phones.
- **Execution risk**: **Active Test** on an authorized segment. Advertising a forged native VLAN to production phones is **Destructive Lab** only.

### Implementation notes

- Each advertisement is built as a CDP version 2 message with the checksum that receivers verify. A receiver that rejects a bad checksum stores nothing, so the lab result also checks the frame.
- The source MAC is the attacker's interface MAC. The fields are the operator's choice: device ID, port, platform, management address and native VLAN (omitted when 0).
- The voice VLAN reply TLV is not built. The lab does not test phone behavior.

### Lab validation

`scripts/lab/cdp_spoofing_lab.sh` runs lldpd in receive-only mode with CDP support as the receiver, and the attacker advertises a switch named MACabre-SW on port FastEthernet0/1, with management address 10.99.0.9 and native VLAN 20. The last run:

- Baseline, CDP enabled, no advertisements: no CDP neighbor stored.
- Attack, CDP enabled: the receiver stored a neighbor named MACabre-SW on port FastEthernet0/1, management address 10.99.0.9, native VLAN 20.
- Control, CDP disabled on the receiver: no neighbor stored.

The lab shows the receiver accepts the forged identity when it keeps CDP neighbors. It does not show the effect on a real Cisco switch, phone or voice VLAN.

## CDP Flooding ✅

**Family**: Discovery & Management Protocols. **Priority**: P1.

- **Protocol**: Cisco Discovery Protocol, version 2 (see CDP Spoofing).
- **Technical reference**: as for CDP Spoofing.
- **Requirements**: root or `CAP_NET_RAW` on a host on the segment with the receiver, and an authorized test network. Flood rates must stay within what the test network can absorb.
- **Compatibility**: receivers that keep a CDP neighbor entry for each device that advertises. Receivers with a neighbor limit, or with CDP disabled on the port, are not affected in the same way.
- **Expected behavior**:
  - Vulnerable: the receiver's neighbor table fills with invented devices, and a legitimate neighbor that appears later is refused or delayed.
  - Protected: CDP is disabled on the flooded port, the neighbor table is limited and aged, or the switch rate-limits CDP.
- **Evidence**:
  - Advertisements sent, with the rate.
  - Neighbor entries stored, before and after the flood.
  - Whether an existing neighbor survives the flood, and whether a neighbor that appears after the flood is stored.
- **Impact**: the neighbor table fills, and legitimate neighbors are missing or delayed. Tools that rely on the table show invented devices.
- **Mitigations**: disable CDP on access and untrusted ports. Limit and age the neighbor table. Rate-limit CDP on the switch where it is supported.
- **Execution risk**: **Active Test** at a low rate on an authorized segment. Flooding a production switch's neighbor table is **Destructive Lab** only.

### Implementation notes

- Each advertisement comes from a random local MAC, with a random device ID, port and address in 10.0.0.0/8. Each one can create a new neighbor.
- The rate is limited to 5000 advertisements per second, sent in batches of 0.1 s.

### Lab validation

`scripts/lab/cdp_flooding_lab.sh` runs lldpd in receive-only mode with CDP support as the receiver. The last run:

- Baseline: one advertisement from SW-LEGIT, 1 neighbor entry stored.
- Flood at 200 advertisements per second for 10 s (2000 sent): 32 neighbor entries stored, and SW-LEGIT still stored.
- Late neighbor, advertised after the flood: SW-LATE was not stored.

The receiver stopped storing new neighbors at 32 entries, whatever the rate. The 32-entry limit belongs to lldpd, not to a Cisco switch, so the lab shows the mechanism and not the switch's table size. CPU use and the effect on a real switch are not measured.

## LLDP Spoofing ✅

**Family**: Discovery & Management Protocols. **Priority**: P1.

- **Protocol**: IEEE 802.1AB Link Layer Discovery Protocol. Frames have EtherType 0x88CC and go to the nearest-bridge group address `01:80:c2:00:00:0e`. Each frame carries type-length-value fields: chassis ID, port ID, TTL, optional port and system description, system name, capabilities, optional management address, and an end marker.
- **Technical reference**: IEEE 802.1AB-2016, LLDP TLVs and the mandatory TLV order.
- **Requirements**: root or `CAP_NET_RAW` on a host on the segment with the receiver, and an authorized test network.
- **Compatibility**: switches, routers and phones that keep LLDP neighbors and act on them. LLDP is enabled by default on most equipment.
- **Expected behavior**:
  - Vulnerable: the receiver stores the forged neighbor, with its system name, port, management address and capabilities.
  - Protected: LLDP receive is disabled on untrusted ports, or the receiver does not use LLDP neighbors for any decision.
- **Evidence**:
  - The neighbor table before and after the advertisements.
  - The system name, port and management address stored, against the advertised values.
  - The same advertisements with LLDP receive disabled on the port.
- **Impact**: a false device appears in the neighbor inventory, and tools that act on LLDP may trust it. A forged management address can point operators to the wrong device.
- **Mitigations**: disable LLDP receive on untrusted and access ports where it is not needed. Use LLDP-MED with a secure voice configuration for phones. Do not treat LLDP neighbors as an inventory.
- **Execution risk**: **Active Test** on an authorized segment. Advertising a forged management address to production equipment is **Destructive Lab** only.

### Implementation notes

- The chassis ID is the attacker's interface MAC by default, and the operator can forge it. The port ID is an interface name, and the TTL is 120 s by default.
- The frame is checked by the receiver's parser. The lab result also depends on the bridge forwarding the reserved LLDP address, which the lab enables with `group_fwd_mask`.
- The management address TLV is IPv4 only, with the interface numbering set to ifIndex 1.

### Lab validation

`scripts/lab/lldp_spoofing_lab.sh` runs lldpd in receive-only mode as the receiver, and the attacker advertises a switch named MACabre-SW on port GigabitEthernet0/1, with management address 10.99.0.9. The last run:

- Baseline, LLDP enabled, no advertisements: no neighbor stored.
- Attack, LLDP enabled: the receiver stored a neighbor named MACabre-SW on port GigabitEthernet0/1, management address 10.99.0.9.
- Control, LLDP receive disabled on the port: no neighbor stored.

The lab shows the receiver accepts the forged identity when it receives LLDP. It does not show the effect on a real switch or phone.

## DHCP Starvation ✅

**Family**: DHCPv4 & DHCPv6. **Priority**: P1.

- **Protocol**: DHCPv4 (BOOTP-based client/server exchange over UDP ports 67 and 68).
- **Technical reference**: RFC 2131 (Dynamic Host Configuration Protocol), RFC 2132 (DHCP options). DHCP snooping is a vendor feature without an RFC; check the device documentation for its configuration.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the same broadcast domain (VLAN) as the DHCP server. No other requirements. The attacker needs no IP address.
- **Compatibility**: DHCPv4 servers with a finite address pool: dnsmasq, ISC DHCP, Windows DHCP, and the DHCP services of routers and switches. Layer 2 access to the segment or VLAN is the only condition.
- **Expected behavior**:
  - Vulnerable: the server offers an address to every client that sends a DISCOVER and then a REQUEST, with no limit per port or per MAC. The pool empties, and a legitimate client that sends a DISCOVER afterwards gets no offer.
  - Protected: DHCP snooping limits DISCOVER rate per port, or port security limits the MAC addresses per port. The server reserves leases per client or enforces a per-relay limit, and the rogue requests are logged.
- **Evidence**:
  - Counts of DISCOVER, OFFER and REQUEST messages sent by the attacker, and the OFFER answers received.
  - Number of leases granted by the server (for example, DHCPACK entries in the server log or the lease file), compared with the pool size.
  - Result of a probe from a legitimate client MAC after the attack: an offer means the pool was not exhausted.
- **Impact**: denial of service for new clients on the segment, loss of connectivity for devices that need a new lease, and a larger attack surface when a rogue DHCP server is later introduced.
- **Mitigations**: DHCP snooping with trusted ports only for DHCP servers, DHCP snooping rate limiting on untrusted ports, port security with a maximum number of MAC addresses, server-side lease limits per MAC or per relay, and monitoring of pool utilization.
- **Execution risk**: **Active Test**, with a limited number of DISCOVER frames. Exhausting a production pool is **Destructive Lab** only.

### Implementation notes

- The attack runs the full handshake: DISCOVER, then the server's OFFER, then REQUEST for the offered address. Completing the handshake is what makes the server commit the lease; a DISCOVER alone only triggers offers. A discover-only option is available for servers that do not commit leases until REQUEST.
- Each DISCOVER uses a random client MAC and a random transaction ID. Offers are matched by transaction ID, so offers meant for other clients are ignored.
- OFFER replies are collected with a sniffer in parallel with the sending. The sniffer has no BPF filter, so it does not depend on libpcap; offers are parsed in Python.
- DHCP message types come from the wire as integers (1 discover, 2 offer, 3 request, 5 ack). The parser maps them to names, and this is covered by tests.
- After the last DISCOVER the attack waits up to 10 seconds for late offers, answering each one until no offer is pending.
- Limitation: the lab disables the dnsmasq ARP check (`--no-ping`), which otherwise delays each offer. That option is for the lab only and does not describe the target server.

### Lab validation

`scripts/lab/dhcp_starvation_lab.sh` runs a dnsmasq server with a 20-address pool on one test host, and the attacker on another. The last run:

- Attacker: 40 DISCOVER, 20 OFFER answered, 20 REQUEST sent.
- Server: 20 DHCPACK, which is 20 of 20 addresses leased.
- Probe with a legitimate MAC afterwards: no offer, because the pool is exhausted.
