# P1 Specifications

Core techniques (priority P1) from the [attack catalog](../attack-catalog.md). The theory behind each attack, which protocols it abuses and why, is in [docs/attacks](../attacks/README.md). Each technique is specified and implemented one at a time, using the same fields:

- **Protocol**: the protocol or mechanism involved.
- **Technical reference**: standard or documentation.
- **Requirements**: what the audit needs (privileges, access, topology).
- **Compatibility**: devices and configurations where the technique applies.
- **Expected behavior**: what a vulnerable and a protected device do.
- **Evidence**: what MACabre collects to prove the result.
- **Impact**: consequences for the network.
- **Mitigations**: controls that prevent or detect the technique.
- **Execution risk**: the operating mode in which the technique may run.

Status legend: ✅ implemented and lab-validated, ⏳ planned.

## MAC Flooding / CAM Overflow ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1Q, bridge learning and forwarding process. Vendor documentation on port security and MAC address limits.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the switch port under test. Layer 2 reachability to the switch. No other requirements.
- **Compatibility**: switches that learn source MAC addresses dynamically. Most managed and unmanaged switches. Devices with port security or MAC limits may stop learning after their limit, which is the expected protected behavior.
- **Expected behavior**:
  - Vulnerable: the switch learns every random source MAC, and unknown unicast frames are flooded to all ports. The table grows until it is full, and the switch may fail open (flood all traffic).
  - Protected: port security limits the learned addresses on the attacked port, and violations are logged or the port is shut down.
- **Evidence**:
  - Number of addresses learned by the switch (for example, from the bridge forwarding table or the switch CAM table).
  - Number of unknown unicast frames received on a monitored port, compared with the number sent.
  - Switch log entries for port security violations, if available.
- **Impact**: traffic flooding on the segment, loss of confidentiality (other hosts' traffic is delivered to the attacker's port), and degraded network performance.
- **Mitigations**: port security with a maximum number of MAC addresses and a violation action (shutdown or restrict), storm control, and monitoring of MAC table growth.
- **Execution risk**: **Active Test**, with a limited frame count and rate. Sustained high rates in production are **Destructive Lab** only.

### Implementation notes

- Frames use a random source MAC and a random unicast destination MAC, with EtherType `0x88B5` (IEEE 802 local experimental), so hosts ignore the payload.
- The attack sends frames only. It does not verify the switch state; the lab script checks the result from the switch side.
- Limitation: the lab uses a Linux bridge, which has no CAM size limit. It measures address learning and unknown-unicast flooding, not a real CAM overflow.

## MAC Flapping ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1Q, bridge learning and forwarding process. Vendor documentation on MAC move detection and loop protection.
- **Requirements**: root or `CAP_NET_RAW` on two interfaces, each attached to a different port of the same switch (or the same VLAN). Layer 2 reachability to the switch.
- **Compatibility**: switches that relearn a MAC address when it appears on another port. Most managed and unmanaged switches. Switches with MAC move detection or port security may shut the port or log the move, which is the expected protected behavior.
- **Expected behavior**:
  - Vulnerable: the switch moves the target MAC entry between the two ports on every frame. Traffic destined to that MAC is delivered to the wrong port or delayed while the entry flaps.
  - Protected: the switch detects the MAC move, logs it, and keeps the entry on the first port (or shuts the port) after a threshold.
- **Evidence**:
  - Number of entry moves for the target MAC, from the switch side (for example, `bridge monitor fdb` on Linux, or the switch MAC move log).
  - Number of distinct ports used by the target MAC in the switch table.
  - Switch log entries for MAC move or port security violations, if available.
- **Impact**: disruption of unicast traffic to the target MAC, intermittent connectivity, and possible misdelivery of frames during the flapping.
- **Mitigations**: MAC move detection and notification, port security with violation actions, loop and flap protection features, and monitoring of MAC table changes.
- **Execution risk**: **Active Test**, with a limited frame count and rate. Sustained flapping of a production MAC is **Destructive Lab** only.

### Implementation notes

- Both interfaces send frames with the same source MAC (the target). A random target is used when none is given. The source MAC is always unicast (the least significant bit of the first octet is 0).
- Frames alternate between the two interfaces, starting with interface A. Destination MAC is random unicast, and EtherType is `0x88B5` (IEEE 802 local experimental), as in MAC flooding.
- The two interfaces must be different. The GUI and the library reject the same interface for both ports.
- The attack sends frames only. The lab script checks the result from the switch side, counting entry moves with `bridge monitor fdb`.

## MAC Address Spoofing ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1Q, bridge learning and forwarding process. Vendor documentation on MAC move detection and port security.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to a switch port in the same VLAN as the target. Layer 2 reachability to the target's segment. The attacker does not need the target's IP address.
- **Compatibility**: switches that relearn a MAC address when it appears on another port. Most managed and unmanaged switches. Switches with MAC move detection or port security may block the move, which is the expected protected behavior.
- **Expected behavior**:
  - Vulnerable: after the spoofed frames, the switch forwards frames addressed to the target MAC to the attacker's port, and the target stops receiving them.
  - Protected: the switch detects the MAC move, logs it, and keeps the entry on the original port (or shuts the attacker's port) after a violation.
- **Evidence**:
  - Switch port for the target MAC before and after the attack (for example, `bridge fdb show` on Linux, or the switch MAC table).
  - Unicast frames addressed to the target, received by the target and by the attacker, before and after the spoofing.
  - Switch log entries for MAC move or port security violations, if available.
- **Impact**: interception of unicast traffic addressed to the impersonated host, denial of service for that host, and a base for man-in-the-middle attacks when combined with forwarding.
- **Mitigations**: static MAC entries for critical hosts, port security with a violation action, MAC move detection and logging, DHCP snooping and dynamic ARP inspection to limit spoofed identities, and 802.1X on access ports.
- **Execution risk**: **Active Test**, with a limited frame count. Sustained spoofing of a production host is **Destructive Lab** only.

### Implementation notes

- The attack sends frames whose source MAC is the target's address, with destination broadcast and EtherType `0x88B5`. The broadcast destination makes the switch learn the source on the attacker's port without relying on a known unicast destination.
- The target MAC is required and must be unicast. The GUI and the library reject empty, invalid, multicast and broadcast values.
- The attack sends frames only. The lab script checks the switch port and the frames received by each host.

### Lab validation

`scripts/lab/mac_spoofing_lab.sh` builds three isolated test hosts on one software bridge: a sender, the target (MAC `02:00:00:00:00:10`) and the attacker. The last run (20 frames from the sender, 5 spoofed frames):

- Baseline: switch port for the target MAC `sw-t`; target received 20 of 20; attacker received 0 of 20.
- After spoofing: switch port `sw-a`; target received 0 of 20; attacker received 20 of 20.

## MAC Cloning ✅

**Family**: MAC Address & CAM Table. **Priority**: P1.

- **Protocol**: IEEE 802.1D MAC learning and forwarding, and IEEE 802.1X or port security access control that admits traffic by MAC address (IEEE 802.3 frames).
- **Technical reference**: IEEE 802.1X (port-based access control). Vendor documentation on port security (sticky or static MAC addresses) and MAC-based access lists.
- **Requirements**: root on the attacking host, and a network interface whose hardware address can be changed. Physical or Layer 2 access to a port that admits a known MAC address, and the MAC address of an authorized device on the segment.
- **Compatibility**: ports with MAC-based access control: port security with a static or sticky MAC address, MAC authentication bypass (MAB), and MAC-based allow lists. Ports protected by 802.1X with certificate or user authentication are not affected by a MAC clone alone.
- **Expected behavior**:
  - Vulnerable: the port admits frames from the cloned address, and the attacker gets network access as the authorized device.
  - Protected: the port rejects frames from an unknown MAC, logs the violation, and shuts down the port. Certificate-based authentication (802.1X) prevents access even with the right MAC.
- **Evidence**:
  - Frames sent from the attacking host with the cloned source MAC, and whether they reach a server on the segment.
  - Frames sent with the attacker's own MAC on the same port, to show that the control was active before the clone.
  - Switch log entries for port security violations, if available.
- **Impact**: unauthorized access to the network as an authorized device, bypass of MAC-based access control, and possible misattribution of traffic to the cloned device in logs.
- **Mitigations**: 802.1X with certificate-based authentication, port security with violation shutdown, DHCP snooping and dynamic ARP inspection to tie identity to address bindings, and monitoring for duplicate or moving MAC addresses.
- **Execution risk**: **Active Test**, with a short window of access. Cloning a production device's MAC is **Destructive Lab** only: the cloned device and the attacker both use the address and can disrupt each other.

### Implementation notes

- The module changes the hardware address of the interface with `ip link` (down, set address, up) and keeps it until the attack is stopped. The original address is read before the change and restored in a `finally` block, so it returns even if setting the clone fails midway.
- Unlike spoofing, cloning affects the whole host: the IP stack and every application send with the cloned address.
- A dry run only prints the planned commands and changes nothing.
- Scapy caches interface MAC addresses when it loads. The module does not use Scapy to read the MAC; the lab reads it with `ip` for the same reason.

### Lab validation

`scripts/lab/mac_cloning_lab.sh` uses a Linux bridge as the switch. Its port for the attacker has an nftables rule that drops frames whose source is not the authorized MAC, which emulates port security with one allowed address. The last run (20 frames per phase):

- Phase 1, attacker's own MAC: the server received 0 of 20 frames. The switch dropped them.
- Phase 2, MAC cloning of the authorized MAC: the host presented the authorized MAC, and the server received 20 of 20 frames. After stopping, the attacker's MAC returned to its original address.

## ARP Spoofing ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet.
- **Technical reference**: RFC 826 (Address Resolution Protocol). RFC 5227 (IPv4 address conflict detection), for the unsolicited-reply behavior hosts must handle. Vendor documentation on Dynamic ARP Inspection.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the victim's broadcast domain (VLAN). The victim's IP and, optionally, its MAC address. No other requirements.
- **Compatibility**: IPv4 hosts that update their ARP cache from unsolicited replies. Most operating systems do so for entries they already hold. Hosts with static ARP entries, and switches with Dynamic ARP Inspection enabled, are not affected by the reply.
- **Expected behavior**:
  - Vulnerable: the victim's cache entry for the spoofed IP changes to the attacker's MAC, and the victim sends that IP's traffic to the attacker.
  - Protected: static ARP entries for critical hosts, Dynamic ARP Inspection drops replies that do not match the DHCP snooping binding table, and the host logs or ignores the unsolicited change.
- **Evidence**:
  - The victim's ARP cache entry for the spoofed IP, before and after the attack (for example, `ip neigh show` on Linux or `arp -a` on other systems).
  - Number of forged replies sent by the attacker, and the MAC they claimed.
  - Switch logs for Dynamic ARP Inspection drops, if available.
- **Impact**: man-in-the-middle position for traffic to the spoofed IP, interception or disruption of the victim's connections, and denial of service if the attacker does not forward traffic.
- **Mitigations**: Dynamic ARP Inspection with DHCP snooping, static ARP entries for gateways and servers, port security on access ports, and monitoring for IP-to-MAC changes.
- **Execution risk**: **Active Test**, with a limited number of replies and a short duration. Poisoning production caches is **Destructive Lab** only: it disrupts every host that talks to the spoofed IP.

### Implementation notes

- Replies are sent with the interface's own MAC (read with `ip`, not Scapy's cache), as both the Ethernet and the ARP sender address.
- Without a victim MAC the reply goes to broadcast. A reply addressed to the victim's MAC is more targeted and less visible on the segment.
- The attack sends replies only. It does not forward traffic, so a victim that loses its gateway will notice. Combining it with IP forwarding is out of scope for this module.

### Lab validation

`scripts/lab/arp_spoofing_lab.sh` uses a Linux bridge with a victim, the real gateway and the attacker. The last run:

- Baseline: the victim's cache for `10.95.0.1` held the gateway's MAC `02:00:00:00:00:01`.
- After 10 forged replies: the entry held the attacker's MAC `02:00:00:00:00:30`.

## ARP Cache Poisoning ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet.
- **Technical reference**: RFC 826 (Address Resolution Protocol). RFC 5227 (IPv4 address conflict detection), for the unsolicited-reply behavior hosts must handle. Vendor documentation on Dynamic ARP Inspection.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the victim's and the gateway's broadcast domain (VLAN). The victim's and the gateway's IP addresses; their MAC addresses are optional.
- **Compatibility**: IPv4 hosts that update existing ARP cache entries from unsolicited replies. Hosts with static ARP entries, and switches with Dynamic ARP Inspection, are not affected.
- **Expected behavior**:
  - Vulnerable: the victim's cache for the gateway and the gateway's cache for the victim both point to the attacker's MAC, so traffic in both directions passes through the attacker.
  - Protected: static ARP entries on the victim and the gateway, Dynamic ARP Inspection, and detection of a single IP claimed by a new MAC.
- **Evidence**:
  - The victim's cache entry for the gateway and the gateway's cache entry for the victim, before and after the attack.
  - Number of rounds and forged replies sent, and the MAC they claimed.
  - Switch or host logs for ARP inspection drops or duplicate-IP detection, if available.
- **Impact**: full man-in-the-middle position between two hosts: interception, modification or denial of their traffic, and credential theft from unencrypted sessions.
- **Mitigations**: Dynamic ARP Inspection with DHCP snooping, static ARP entries for critical hosts, port security, 802.1X, encrypted protocols end to end, and monitoring for IP-to-MAC changes.
- **Execution risk**: **Active Test**, with a short duration and a limited number of rounds. Poisoning production hosts is **Destructive Lab** only: it intercepts their live traffic.

### Implementation notes

- Each round sends two replies: one to the victim (gateway IP at the attacker's MAC) and one to the gateway (victim IP at the attacker's MAC). Repeated rounds keep the entries from expiring.
- The attacker's MAC is read with `ip`, not from Scapy's cache.
- The module poisons caches only. It does not forward traffic, so a connection between the victim and the gateway stops working until forwarding is enabled on the attacker. Forwarding is out of scope for this module.
- The difference from ARP spoofing is the scope: ARP spoofing sends one forged binding to one host; cache poisoning poisons both ends and keeps them poisoned.

### Lab validation

`scripts/lab/arp_poisoning_lab.sh` uses a Linux bridge with a victim, the gateway and the attacker. The last run (6 rounds, 12 forged replies):

- Baseline: the victim's cache for the gateway held `02:00:00:00:00:01`, and the gateway's cache for the victim held `02:00:00:00:00:10`.
- After poisoning: both caches held the attacker's MAC `02:00:00:00:00:30`.

## Gratuitous ARP Spoofing ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`). Gratuitous ARP is an unsolicited ARP request whose sender and target IP are the same address.
- **Technical reference**: RFC 826 (Address Resolution Protocol). RFC 5227 (IPv4 address conflict detection), which defines the announcement and the behavior of hosts that receive it.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the segment. The IP address to announce. No victim address is needed.
- **Compatibility**: IPv4 hosts that update existing ARP cache entries from announcements. Most operating systems do so. Hosts with static entries, and switches with Dynamic ARP Inspection, are not affected.
- **Expected behavior**:
  - Vulnerable: every host on the segment that caches the announced IP updates its entry to the attacker's MAC, from a single broadcast.
  - Protected: static ARP entries, Dynamic ARP Inspection, and duplicate-address detection that flags an IP announced by a new MAC.
- **Evidence**:
  - The ARP cache entry for the announced IP on each host, before and after the announcements.
  - Number of announcements sent and the MAC they claimed.
  - Host or switch logs for address conflicts or ARP inspection drops, if available.
- **Impact**: traffic to the announced IP is redirected on the whole segment, which is wider than one victim. Hosts that depend on that IP lose connectivity or send it to the attacker.
- **Mitigations**: Dynamic ARP Inspection with DHCP snooping, static ARP entries for gateways and servers, duplicate-address detection, and monitoring for IP-to-MAC changes.
- **Execution risk**: **Active Test**, with a limited number of announcements. Announcing a production gateway's IP is **Destructive Lab** only: it affects every host on the segment.

### Implementation notes

- The announcement is an ARP request with sender and target IP equal to the announced address, sent to broadcast with the target MAC set to zero. This is the form `arping -A` produces.
- The attacker's MAC is read with `ip`, not from Scapy's cache.
- The difference from ARP spoofing is the scope: spoofing targets one host, and a gratuitous announcement reaches every host that caches the IP.

### Lab validation

`scripts/lab/gratuitous_arp_lab.sh` uses a Linux bridge with two victims, the gateway and the attacker. The last run (3 announcements from one broadcast each):

- Baseline: both victims cached the gateway as `02:00:00:00:00:01`.
- After the announcements: both victims cached `02:00:00:00:00:30`, the attacker's MAC.

## ARP Request Flooding ✅

**Family**: ARP. **Priority**: P1.

- **Protocol**: Address Resolution Protocol over Ethernet (EtherType `0x0806`), IPv4 on Ethernet.
- **Technical reference**: RFC 826 (Address Resolution Protocol). Vendor documentation on ARP rate limiting, neighbor table size limits (for example the Linux `gc_thresh` settings) and CoPP.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the segment. The subnet to draw sender and target addresses from. No other requirements.
- **Compatibility**: any IPv4 segment. The effect depends on how many requests the hosts and the router process per second, and on the size of their neighbor tables.
- **Expected behavior**:
  - Vulnerable: every host processes each broadcast request, and the host that owns the target IP answers each sender, so its neighbor table grows with every distinct sender. High rates raise CPU load on the hosts and the router.
  - Protected: ARP rate limiting or control-plane policing on the router, bounded neighbor tables with eviction, and ARP inspection that drops requests from senders the switch did not learn.
- **Evidence**:
  - Requests received by a monitored host during the flood, compared with the number sent.
  - Neighbor table size on the target host, before and after the flood.
  - Switch or router logs for ARP rate limits or neighbor table overflow, if available.
- **Impact**: degraded performance of every host on the segment, neighbor table exhaustion on the router (new hosts cannot be resolved), and loss of connectivity for hosts whose entries are evicted.
- **Mitigations**: ARP rate limiting and control-plane policing, bounded neighbor tables with eviction policies, port-based ARP rate limits on the switch, and ARP inspection.
- **Execution risk**: **Active Test**, with a limited number of requests. Flooding a production segment is **Destructive Lab** only.

### Implementation notes

- Each request has a random unicast sender MAC and a random sender IP from the subnet, and is sent to broadcast.
- The target is a fixed IP, for example the gateway, which makes the target answer every sender and fill its table. Without a fixed target the requests ask for random hosts of the subnet.
- With a fixed target and a /24 subnet, random senders repeat, so the neighbor table grows to roughly the number of distinct sender IPs, not to the request count.
- The attacker's own MAC is not used as sender: every request carries a random one. The attacker can only be identified by the interface it sends from.

### Lab validation

`scripts/lab/arp_request_flooding_lab.sh` uses a Linux bridge with a victim, the gateway and the attacker. The last run (200 requests for the gateway's IP):

- The victim received 200 of 200 flooded requests.
- The gateway's neighbor table went from 1 entry to 133. The subnet has 254 hosts, so repeated random senders account for the difference from 200.

## DHCP Starvation ✅

**Family**: DHCPv4 & DHCPv6. **Priority**: P1.

- **Protocol**: DHCPv4 (BOOTP-based client/server exchange over UDP ports 67 and 68).
- **Technical reference**: RFC 2131 (Dynamic Host Configuration Protocol), RFC 2132 (DHCP options). DHCP snooping is a vendor feature without an RFC; check the device documentation for its configuration.
- **Requirements**: root or `CAP_NET_RAW` on an interface attached to the same broadcast domain (VLAN) as the DHCP server. No other requirements. The attacker needs no IP address.
- **Compatibility**: DHCPv4 servers with a finite address pool: dnsmasq, ISC DHCP, Windows DHCP, and the DHCP services of routers and switches. Layer 2 access to the segment or VLAN is the only condition.
- **Expected behavior**:
  - Vulnerable: the server offers an address to every client that sends a DISCOVER and then a REQUEST, with no limit per port or per MAC. The pool empties, and a legitimate client that sends a DISCOVER afterwards gets no offer.
  - Protected: DHCP snooping limits DISCOVER rate per port, or port security limits the MAC addresses per port. The server reserves leases per client or enforces a per-relay limit, and the rogue requests are logged.
- **Evidence**:
  - Counts of DISCOVER, OFFER and REQUEST messages sent by the attacker, and the OFFER answers received.
  - Number of leases granted by the server (for example, DHCPACK entries in the server log or the lease file), compared with the pool size.
  - Result of a probe from a legitimate client MAC after the attack: an offer means the pool was not exhausted.
- **Impact**: denial of service for new clients on the segment, loss of connectivity for devices that need a new lease, and a larger attack surface when a rogue DHCP server is later introduced.
- **Mitigations**: DHCP snooping with trusted ports only for DHCP servers, DHCP snooping rate limiting on untrusted ports, port security with a maximum number of MAC addresses, server-side lease limits per MAC or per relay, and monitoring of pool utilization.
- **Execution risk**: **Active Test**, with a limited number of DISCOVER frames. Exhausting a production pool is **Destructive Lab** only.

### Implementation notes

- The attack runs the full handshake: DISCOVER, then the server's OFFER, then REQUEST for the offered address. Completing the handshake is what makes the server commit the lease; a DISCOVER alone only triggers offers. A discover-only option is available for servers that do not commit leases until REQUEST.
- Each DISCOVER uses a random client MAC and a random transaction ID. Offers are matched by transaction ID, so offers meant for other clients are ignored.
- OFFER replies are collected with a sniffer in parallel with the sending. The sniffer has no BPF filter, so it does not depend on libpcap; offers are parsed in Python.
- DHCP message types come from the wire as integers (1 discover, 2 offer, 3 request, 5 ack). The parser maps them to names, and this is covered by tests.
- After the last DISCOVER the attack waits up to 10 seconds for late offers, answering each one until no offer is pending.
- Limitation: the lab disables the dnsmasq ARP check (`--no-ping`), which otherwise delays each offer. That option is for the lab only and does not describe the target server.

### Lab validation

`scripts/lab/dhcp_starvation_lab.sh` runs a dnsmasq server with a 20-address pool on one test host, and the attacker on another. The last run:

- Attacker: 40 DISCOVER, 20 OFFER answered, 20 REQUEST sent.
- Server: 20 DHCPACK, which is 20 of 20 addresses leased.
- Probe with a legitimate MAC afterwards: no offer, because the pool is exhausted.
